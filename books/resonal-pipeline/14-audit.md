---
title: "記録と見張り — 完了は機械が判定する"
---

この章では、リリース作業が本当に終わったかを機械で判定する仕組みと、リリース後に毎晩行っている監査、引き継ぎのための記録について説明します。

## 完了を判定する finalize.sh

第13章の `release.sh` は、リリースの6項目だけを行います。しかし、1曲を終えるには、ほかにも作業があります。例えば、SoundCloud 用のジャケット画像、YouTube の歌詞字幕、引き継ぎメモなどです。

これらを含めて「完了」を判定するのが `finalize.sh` です。

```bash
./release/finalize.sh "<曲フォルダ>" --date=2026-09-21
```

`finalize.sh` は、次の順に動きます。

1. 第15章で説明する `checklist.js` の全項目を検査する
2. 機械で埋められる項目（ジャケット画像の生成、YouTube の予約など）が未了なら、その場で埋めて、もう一度検査する
3. 未了の数が減らなくなったら止める
4. 残った項目を「何をすればよいか」付きで列挙して、exit code 1 で終わる
5. 未了がなければ exit code 0 で終わる

exit code は、プログラムが終わるときに返す数値です。0 が成功、それ以外が失敗を表します。

2の「埋めて、もう一度検査する」部分は次のとおりです。

```js:release/finalize.js
    if (it.who === 'auto' && it.fix) {
      console.log(`  [fix] ${it.id} — ${r}`);
      try {
        it.fix(ctx);
        const again = checkOne(it);
        if (again === true) { fixedThisRound.push(it.id); continue; }
        pending.push({ it, reason: again });
      } catch (e) {
        pending.push({ it, reason: `fix が失敗: ${e.message}` });
      }
```

埋める処理（`fix`）が成功したかどうかは、埋める処理の戻り値ではなく、もう一度検査した結果で判断しています。

AI には、exit code 0 が返るまでこのコマンドを繰り返すよう指示しています。0 を見ないまま「完了しました」と報告することは禁止しています。

### 項目が揃っても、実際の状態を確かめる

`finalize.sh` は、検査項目が揃ったあとに、もう1段の確認をします。次の節で説明する監査スクリプトを、この曲だけに対して実行します。

```zsh:release/finalize.sh
node "$HERE/finalize.js" "$@"
RC=$?
[ "$RC" -ne 0 ] && exit "$RC"     # checklist が未了＝ここで止まる（audit まで行かない）

# ---- 実態の突合（--song で対象曲だけ／未リリース曲も見る） ----
echo ""
echo "━━━ 実態の突合（release-audit）━━━"
node "$HERE/release-audit.js" --song "$SONG"
AR=$?
```

この段を足したのは、検査項目だけでは見逃しがあったためです。リリースの項目は「`release.json` に YouTube の動画 ID が入ったか」だけで完了と判定していました。また、その中で呼ぶ `release.sh` は、途中で失敗しても処理を続けます。そのため、YouTube のアップロードさえ通れば完了と判定され、SNS の予告やプレイリストなどが未完のまま exit code 0 になることがありました。実際に、ある曲で5件を見逃していました。

いまは、監査で違反が見つかれば、検査項目が揃っていても exit code 0 にはなりません。

## 毎晩20時の監査 release-audit

mac mini では、毎晩20:00に `release-audit.js` を launchd（macOS で決まった時刻に処理を動かす仕組み）で実行しています。本編の公開が19:00、ショートの自動公開が19:10なので、その直後に結果を確かめる時刻にしています。

監査の対象は、リリースが始まっている曲です。YouTube の動画 ID か、配信サービスへの入稿日が記録されている曲を対象にします。

主に次の項目を確かめています。

| 項目 | 確かめること | 何と照らし合わせるか |
|---|---|---|
| 本編 | 公開時刻を過ぎた本編が公開されている。未来の予約は、YouTube 側に公開時刻が実際に入っている | YouTube API |
| タイトル | アップロード用のメタデータと、実際の動画のタイトルが同じ | YouTube API |
| ショート | 公開済みの曲はショートが commented まで進んでいる。公開前の曲は非公開でアップロード済みで、公開日の処理が登録されている | YouTube API、LaunchAgents（launchd の登録ファイル） |
| SNS | 予告が予約されている。公開日の告知が実際に投稿された | 投稿の予約キュー、告知の記録 |
| 毎日のショート | 1日1本を守っている。同じ曲を2日続けていない。1本も出ていない日がない | 投稿の記録（post-ledger） |
| 配信サービス | 入稿済みである | `release.json` の入稿日 |
| 検査項目 | `checklist.js` の項目が揃っている | 曲フォルダ |
| アップロードの中身 | YouTube に上がっている動画が、手元の納品ファイルと同じ | YouTube API（次の節） |
| ショートのリンク | 公開済みのショートに本編へのリンクが付いている | 公開ページ（次の次の節） |
| トークン | YouTube のトークンに、コメント投稿に必要な権限がある | トークンファイル |

「本編」の未来の予約を確かめるようにしたのは、2026年8月の Cotton Overkill がきっかけです。それまでは「公開時刻を過ぎたら公開されているか」だけを見ていたので、公開時刻が設定されていない非公開の動画を正常として通していました。そのままでは、公開日になっても公開されません。

なお、配信サービスの項目は `release.json` の入稿日を見ているだけで、配信サービス側の実際の状態は確かめていません。

### 通知は違反があったときだけ

違反が1件もなければ、Slack には何も送りません。

```js:release/release-audit.js
  if (!violations.length) {
    console.log('違反なし ✨');
    process.exit(0);
  }
```

違反があったときは、件数と内容、直すためのコマンドを Slack に送ります。直すためのコマンドは、多くの場合 `./release/release.sh "<曲>"` です。第13章で説明したとおり、何度実行しても同じ結果になるので、違反が出たらもう一度実行すれば足りない項目だけが進みます。

また、監査そのものが失敗したときも Slack に送ります。例えば、YouTube のトークンが失効すると、API を呼べずに監査が途中で止まります。このとき何も送らないと、「違反がないので静か」なのか「監査が動いていないので静か」なのかが区別できません。

```js:release/release-audit.js
})().catch((e) => {
  console.error('[audit error]', e.message);
  // audit自体が死んだら（YouTubeトークン失効=invalid_grant等）それも鳴らす＝監視の監視
  if (flags.slack) {
    try { execFileSync(SLACK, [`⚠️ release-audit の実行自体が失敗: ${e.message}\n（invalid_grant なら youtube-upload で npm run auth）`], { stdio: 'ignore' }); } catch {}
  }
  process.exit(2);
});
```

## アップロードした動画を、手元のファイルとバイト単位で比べる

`verify-uploads.js` は、YouTube に上がっている動画が、手元の納品ファイルと同じかを確かめるスクリプトです。

きっかけは、2026年9月のおかわりアポカリプスです。アップロードのスクリプトが「曲フォルダの中で、ショート以外で最もサイズが大きい動画」を本編として選ぶ作りになっていました。そのため、曲フォルダに残っていたマスタリング前の動画（469MB）が、納品版（416MB）より大きく、こちらが本編として公開されていました。僕が「本編も古い動画がアップされてる？」と指摘するまで、機械では検知できていませんでした。

気づけなかった理由は、次の3つです。

- `release.json` には動画 ID しか記録しておらず、どのファイルを上げたかの記録がなかった
- マスタリング前の動画も納品版も、長さは同じ186秒だった
- 音量を測れば違いは分かるが、非公開の予約動画はダウンロードできず、公開前に測れなかった

そこで、YouTube の API が返すファイルサイズを使うことにしました。アップロードした実体のバイト数で、動画の所有者であれば非公開でも読めます。

```js:youtube-upload/verify-uploads.js
    const localSize = local ? fs.statSync(local).size : null;
    let verdict;
    if (!m.size) verdict = 'NO-META';
    else if (!local) verdict = 'NO-LOCAL';
    else verdict = Number(m.size) === localSize ? 'OK' : 'MISMATCH';
```

手元のファイルとバイト数が一致しなければ、別のファイルが上がっていると判定します。このスクリプトは毎晩20時以降に動き、結果をファイルに書きます。監査はその結果を読み、48時間以上更新されていないか、一致しない動画があれば通知します。

アップロードのスクリプト側も、決まったファイル名の動画だけを選ぶように直しました。ただ、それはこれからアップロードする動画にしか効果がないので、すでに上がっている動画はこの照合で確かめています。

## ショートから本編へのリンクを確かめる

ショートには、本編へのリンク（YouTube の「関連動画」）を付けています。ショートを見た方が、本編に移れるようにするためです。

このリンクは、YouTube の API では設定も読み出しもできません。そのため、リンクを付ける処理は失敗しやすく、失敗しても気づきにくい状態でした。

そこで、`link-shorts-audit.js` で、公開済みのショートのページを取得し、本編の動画 ID が載っているかで判定しています。この結果も毎晩ファイルに書き、監査が「リンクがないショートが何本あるか」を数えて通知します。

## 引き継ぎメモと制作ログ

1曲が終わったら、2つの記録を残しています。

**引き継ぎメモ `HANDOFF.md`** は、曲フォルダに置くメモです。確定した仕様の表と、次の曲に活かせる学びを優先度順に書きます。経緯の細部は企画書や歌詞のファイルに任せ、ここには要点だけを書きます。例えば Stutter Step の `HANDOFF.md` には、9つの学びを書いています。

**制作ログ `collab-log-ayase-apoto.md`** は、リポジトリ直下に1つだけあるファイルです。僕と彩瀬??のやり取り（「ここ違う」「もっとこう」という直しの応酬）、決まったこと、採用しなかった案を、曲ごとに追記しています。2026年9月時点で4,000行を超えていて、SNS で制作の裏側を投稿するときのネタ元にしています。

どちらも `checklist.js` の項目になっていて、書き忘れると `finalize.sh` が止まります。ただし、検査しているのは、引き継ぎメモのファイルがあるか、制作ログに曲名が出てくるかだけです。中身が十分かどうかは、機械では判定していません。

## まとめ

`finalize.sh` は、機械で埋められる項目を埋めてから検査し直し、残りを列挙して exit code 1 で止まります。検査項目が揃ったあとも、監査で実際の状態を確かめて、はじめて exit code 0 を返します。毎晩20時の監査は、YouTube の API や投稿の記録と照らし合わせ、ズレがあるときだけ Slack に通知します。監査そのものが失敗したときも、Slack に通知します。
