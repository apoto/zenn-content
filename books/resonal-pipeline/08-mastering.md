title: "マスタリング — 毎回同じ数値に着地させる"
---

この章では、RESONAL のマスタリングをどう自動化しているかを説明します。展示会では「マスタリングも自動なのか」という質問を多くいただいたので、目標にしている数値と、そこへ着地させる処理を順に紹介します。

## マスタリングとは

マスタリングは、完成した曲の音量や音色を整えて、配信できる状態の音源に仕上げる工程です。例えば、低音がこもっていれば削り、音量が小さければ持ち上げ、音が割れないように上限を決めます。RESONAL では、Suno が生成したステレオの音源（以下、プレマスター）を入力にして、配信用の `<曲名>.wav` を作るところまでをマスタリングと呼んでいます。

この章で出てくる3つの用語は、次の意味です。

- **LUFS**：人の耳の感じ方に合わせて測った音量の単位です。曲全体の平均を Integrated（インテグレーテッド）と呼びます
- **True Peak（dBTP）**：デジタルの音のサンプルとサンプルの間まで補って測った、本当のピークの値です
- **LRA（LU）**：曲の中で、静かな部分と大きな部分の音量がどれくらい離れているかを表す値です

## 毎回同じにする数値と、揃えない数値

RESONAL では、どの曲でも同じ値に着地させる項目を `MASTERING.md` の §1 に決めています。

| 項目 | 基準値 |
|---|---|
| True Peak の天井 | -1.5 dBTP |
| Integrated | -9.5 ± 0.5 LUFS（-9.0〜-10.0 に着地） |
| 書き出し形式 | 48kHz / 24bit の WAV |
| ディザ | 16bit に変換するときだけ ON（24bit で納品するなら OFF） |

それぞれの理由も、同じ表に書いています。True Peak を -1.5 にしているのは、AAC や MP3 などに変換したときにエンコーダで音が割れるのを防ぐためです。Integrated を揃えているのは、チャンネルを連続再生したときやプレイリストで、曲ごとの音量差を出さないためです。配信サービスでは音量が正規化されるのでこの差は消えますが、手元の WAV と視聴したときの印象を揃える意味があると書いています。

48kHz にしているのは、Suno の音源が 48kHz で、YouTube の動画の音声も 48kHz が標準だからです。こうすると、Suno から MV、YouTube まで一度もサンプルレートの変換が入りません。以前は 44.1kHz でしたが、2026年7月18日に変更しました。

一方で、LRA は揃えていません。`MASTERING.md` の §2 には「曲調で変動して当然。Drop のある曲は広め、詰めた曲は狭め」と書いています。全曲を同じ値に合わせると、それぞれの曲の個性がなくなってしまうためです。

## 手作業から自動化までの経緯

最初のころは、Cubase に iZotope Ozone Standard（マスタリング用のプラグイン）を挿して、僕が手で調整していました。各数値は彩瀬??に聞きながら決めていて、曲ごとに Ozone の設定値と実測値を `MASTERING.md` の §5 に記録しています。

2026年7月には、音色の方向性を「耳の抜け感」と決めました。DistroKid のマスタリングサービス Mixea と、Prism の手作業のマスターを実測で比べたところ、Mixea のほうが中域から高域への落ち込みが小さかったためです。そこで、低中域（400Hz〜1kHz あたり）を少し削り、中〜高域を開ける調整を標準にしました。

2026年8月11日に、Ozone を使わず ffmpeg だけで完結する `auto_master.py` を作りました。Ozone が入っていない mac mini でも回せるようにするためです。最初の版は、matchering（お手本の曲に音色を寄せるオープンソースのライブラリ）で参照曲に寄せる方式でした。しかし、Cold Read で手作業のマスターとブラインドで聴き比べたところ、僕は手作業のほうを選びました。参照曲の低音が Cold Read より薄く、自動のほうは低音が痩せていたためです。

翌日、方式を作り替えました。手作業のときも毎回ほぼ同じ処理をしていたので、それをテンプレートにして、Ozone と自動処理の両方で同じテンプレートを使うことにしました。作り替えた版で再びブラインドで聴き比べると、僕は自動のほうを選び、手作業のほうを「若干シャリつく」と感じました。これ以降の曲は、自動のマスターで配信しています。

## auto_master.py の処理の流れ

現在の `auto_master.py` は、次の順で処理します。

1. すでにマスタリング済みの音源が入力されていないかを確認する
2. 48kHz / 24bit の WAV に変換する
3. 固定のイコライザで音色を整える（トーン段）
4. ゲインとリミッタで、目標の数値に着地させる
5. 基準を満たしているかを判定する
6. 実測レポート `MASTER-AUTO.md` を書き出す
7. 聴き比べ用の音源を Slack に送り、問題なければ `--promote` で昇格する

### 二重マスタリングを防いでから、48kHz に変換する

最初に、入力の Integrated を測ります。-12 LUFS より大きい場合は、すでにマスタリング済みの音源とみなして止めます。マスタリング済みの音源にもう一度処理をかけると、音を二重に潰すことになるためです。

```python:.claude/skills/mixmaster-resonal/scripts/auto_master.py
pre = loudness(src)
print(f"[in ] {src.name}: I={pre['I']} LUFS / TP={pre['TP']} dBTP / LRA={pre['LRA']} LU")
if not args.force and (pre["I"] or -99) > -12.0:
    sys.exit(f"[ERR] 既にマスター済みに見える（I={pre['I']} LUFS > -12）。二重マスターは禁止。"
             f"\n  premaster（Suno源/ミックスのバウンス）を渡す。意図的なら --force。")
```

次に、入力を 48kHz / 24bit の WAV に変換します。入力が MP3 でも、変換はここで1回だけです。

### トーン段は、固定のイコライザを当てる

トーン段の既定は「House テンプレート」です。これは、どの曲にも同じイコライザのカーブを当てる処理で、別の曲に音色を寄せる処理ではありません。

```python:.claude/skills/mixmaster-resonal/scripts/auto_master.py
chain = [
    "highpass=f=28",                                              # subの下だけ落とす（sub残す）
    f"lowshelf=f=100:g={k['low']:.2f}",                           # 低域の土台（Ozone の Low End Focus 相当）
    f"equalizer=f=550:width_type=q:w=0.7:g={k['scoop']:.2f}",     # 箱鳴りスクープ（抜けの前提）
    f"equalizer=f=3300:width_type=q:w=1.2:g={k['presence']:.2f}", # presence（歌/リード前へ）
    f"highshelf=f=7000:g={k['shelf7k']:.2f}",                     # ★抜けの主役（5-10k帯）
    f"equalizer=f=8500:width_type=q:w=1.0:g={k['harsh']:.2f}",     # 刺さり抑え（Ozone Dynamic EQ 相当の静的版）
    f"equalizer=f=12000:width_type=q:w=1.0:g={k['air']:.2f}",     # air 控えめ（生ブーストは最小）
]
```

各帯域をどれくらい上げ下げするかは、`bright` / `neutral`（既定） / `sub-driven` / `dark` の4つのプロファイルで切り替えます。例えば `neutral` は、100Hz を +2.5dB、550Hz を -1.2dB、7kHz から上を +1.5dB にします。プロファイルは、元の音源の明るさや低音の量を見て選びます。

matchering で参照曲に寄せる方式も残していますが、`--engine matchering` を指定したときしか動きません。`--ref` や `--archetype` だけを渡すとエラーで止まるようにしています。僕から「間違って matchering が先に動かないようにしてほしい」と頼んだためです。参照曲は、ジャンルごとに1曲ずつ決めています。

### 着地ループで、目標の数値に合わせる

トーン段の後は、ゲインとリミッタで目標の数値に合わせます。リミッタは、音が天井を超えそうなときに先読みして音量を下げる処理で、ffmpeg の `alimiter` を使っています。

1周ごとに、ゲインを掛け、サンプルレートを4倍（192kHz）に上げてリミッタを掛け、48kHz に戻してから実測します。4倍に上げているのは、サンプルとサンプルの間のピークを捉えるためです。`MASTERING.md` によると、48kHz のまま天井を -1.7 に抑えても、実測の True Peak は -0.8 dBTP まで漏れました。4倍にして掛けると -1.6 に収まりました。

実測した後は、次のように判断します。

```python:.claude/skills/mixmaster-resonal/scripts/auto_master.py
di = TARGET_I - (m["I"] or TARGET_I)
print(f"[final #{attempt}] gain={gain:+.2f}dB ceiling={ceiling:.2f}dBFS (OS×{OVERSAMPLE}) "
      f"→ I={m['I']} LUFS / TP={m['TP']} dBTP / LRA={m['LRA']} LU")
tp_over = (m["TP"] or -99) - TARGET_TP
if tp_over > 0.0:                      # TP は死守。天井を下げてやり直す
    ceiling -= tp_over + 0.05
    continue
if abs(di) > 0.15:                      # ラウドネスを合わせる
    gain += di
    continue
return last
```

True Peak が -1.5 を超えていれば、リミッタの天井を下げてやり直します。Integrated が目標から 0.15 より大きくずれていれば、その差だけゲインを足してやり直します。これを7周まで繰り返します。

目標の Integrated は、-9.5 ではなく -9.7 にしています（コード上の `TARGET_I`）。許容範囲の静かめの側に置くと、リミッタで下げる量が減って、音量の幅（LRA）が残るためです。Prism で試したところ、-9.4 を狙うと LRA は 2.5、-9.7 を狙うと 2.9 でした。

## 測定には ffmpeg の ebur128 を使う

Integrated・LRA・True Peak の測定は、どこでも同じ ffmpeg のコマンドを使っています。

```bash
ffmpeg -hide_banner -nostats -i "<ファイル>" -af ebur128=peak=true:framelog=quiet -f null -
```

出力の最後にある `I:`（Integrated）、`LRA:`、`Peak:`（True Peak）の値を読み取ります。サンプルレートとビット深度は ffprobe で確認します。`auto_master.py` も、後で説明する `checklist.js` も、このコマンドで測っています。

## 基準を満たしているかを判定する

着地した音源は、次のどれかに当てはまると NG になります。

| NG の条件 | 意味 |
|---|---|
| True Peak が -1.5 dBTP を超えている | 天井を守れていない |
| Integrated が -10.0〜-9.0 LUFS の外 | 音量が基準から外れている |
| サンプルレートが 48000Hz でない | 変換が入っている |
| ビット深度が 24bit でない | 書き出し形式が違う |
| LRA がプレマスターより 1.0 より多く減り、かつ 3.0 未満 | 潰しすぎ |
| Flat factor が 1.0 を超えている | 波形の頭が平らに切れている（クリップの疑い） |

LRA の条件を2つ組み合わせているのは、誤判定を避けるためです。プレマスターとの差だけで判定すると、元の LRA が大きい曲（Cold Read は 5.0）は、普通の値に着地しただけで NG になってしまいます。逆に LRA の値だけで判定すると、元から LRA が小さい曲（おかわりアポカリプス）が NG になりました。

判定の結果は、実測値と一緒に `MASTER-AUTO.md` に書き出します。例えば Heat Shock では、次のようになりました。

```markdown:260923_Heat Shock/MASTER-AUTO.md
- 入力(premaster): I=-15.5 LUFS / TP=-3.5 dBTP / LRA=6.3 LU
- 出力(auto):      I=-9.8 LUFS / TP=-1.7 dBTP / LRA=4.5 LU / 48000Hz 24bit
- エンジン:        House テンプレート（matchering=OFF・ハウスカーブ相対適用）
- クリップ検査:    Flat factor=0.00 / Peak count=2（リミッタで丸めた音は ≈0。クリップすると立つ）
```

LRA は 6.3 から 4.5 に減っていますが、3.0 以上なので NG にはなりません。レポートには、帯域ごとの音量と、低域と中域、中域と高域の差も書き出します。

## 聴き比べてから昇格する

`auto_master.py` の出力は、いったん `<曲名>_automaster.wav` という候補として保存します。配信や MV に使う `<曲名>.wav` にするのは、`--promote` を付けて昇格させたときだけです。昇格は判定が PASS のときしかできず、同時に `MASTERING.md` §5 の記録表に1行を追記します。

手作業のマスターがある曲では、`ab_blind_master.sh` で聴き比べ用の音源を作ります。2つの音源を -14 LUFS にゲインだけで揃え、RED と BLUE という名前をランダムに付けて Slack に送ります。どちらがどちらかは別のファイルに記録し、判定が終わるまで開きません。生の音源を並べると、音量が大きいほうが良く聞こえてしまうためです。

手作業のマスターが無い曲では、曲の中で最も音量が大きい30秒を切り出し、プレマスターと候補を並べて Slack に送ります。

【要確認: 手マスターが無い現在の運用で、昇格の前に apoto が Slack の抜粋を聴いて判断しているか。checklist の指示文は「実測が基準内なら --promote」】

## 後工程での照合

マスタリングが終わった後も、別の工程で数値を照合しています。

### checklist の MASTER 項目

`checklist.js` の MASTER 項目は、`<曲名>.wav` を ffmpeg で測り、`MASTERING.md` §1 の基準と比べます。基準値はコードに書かず、`MASTERING.md` の表から読み取っています。基準を変えるときに、書き換える場所を1つにするためです。

```js:release/checklist.js
if (Math.abs(m.lufs - spec.lufs) > spec.lufsTol)
  return `Integrated ${m.lufs} LUFS（基準 ${spec.lufs}±${spec.lufsTol}）＝マスタリングが未了か外れている`;
if (m.tp !== null && m.tp > spec.tpCeil + 0.3)
  return `True Peak ${m.tp} dBTP（天井 ${spec.tpCeil}）`;
```

True Peak は天井に 0.3dB の余裕を持たせて判定しています。【要確認: +0.3 の理由（コードにコメントなし）】

### MV-FILES 項目

MV と YouTube と配信サービスは、同じ1つのマスター WAV から作ります。YouTube Music は、配信サービス向けに納品した音源と、チャンネルの MV の両方を再生するためです。MV の音がプレマスターのままだと、視聴者はマスタリング前の音を聞くことになります。

そこで、MV-FILES 項目では、納品する動画の音とマスター WAV の Integrated を比べます。

```js:release/checklist.js
const mm = ctx.loudness(mp);
const vm = ctx.loudness(path.join(ctx.dir, d.main));
if (mm && vm && Math.abs(mm.lufs - vm.lufs) > 0.8)
  return `本編の音がマスターと違う（本編 ${vm.lufs} / master ${mm.lufs} LUFS）＝仮組み音源でレンダーした疑い`;
```

差が 0.8 LUFS を超えると、仮組みの音源で動画を書き出した疑いがあるとして止めます。動画に設定したファイル名は見ていません。ファイル名が同じでも、中身が違うことがあるためです。レンダーについては第12章で説明します。

### アップロードした動画との照合

最後に、YouTube にアップロードした動画と、手元の納品ファイルが同じものかを照合しています。`verify-uploads.js` が、YouTube Data API で取得したファイルサイズと、手元の mp4 のバイト数を比べます。

これは、おかわりアポカリプスで起きた事故がきっかけです。アップロードのスクリプトが「ショート以外で最もサイズが大きい mp4」を本編に選ぶ作りになっていて、曲フォルダに残っていたマスタリング前の動画（469MB）が、納品版（416MB）より大きかったため、そちらが公開されてしまいました。2つの動画は尺が同じで、非公開の予約動画は音を取得できないため、尺や音量では見分けられませんでした。一方で、ファイルサイズは所有者なら非公開の動画でも取得できるので、公開前に確認できます。この照合は毎晩20時以降に実行し、結果は毎晩の監査が読みます（第13章）。

## 生成された音源の長さは編集しない

マスタリングでは、音源の長さを変えません。器楽のイントロやアウトロ、最後の余韻を切ることを禁止しています。Suno への発注で「イントロ無し」「ぴたっと終わる」と指定していても、出てきた音源の長さを正とします。

`MASTERING.md` §2.5 には、その理由を「発注意図と生成結果がズレたとき、こちらの意図に合わせて切るのは作品を設計図に合わせて削ること」と書いています。長さが気に入らなければ、切るのではなく生成し直します。曲の前後に配信用の無音を足すことと、音量や音色の処理は認めています。

MV-FILES 項目では、動画とマスター WAV の長さの差が2秒を超えていないかも確認しています。長さを編集しないので、この2つは常にほぼ同じ長さになるはずだからです。

## 自動化していないこと

`MASTER-AUTO.md` の末尾には、「自動でやらないこと（人の判断が要る）」として次の項目を書いています。

- **プロファイルの選択**：`bright` / `neutral` / `sub-driven` / `dark` のどれを使うか。ずれると、抜けや低音の量が他の曲と離れてしまいます
- **最後の可否判断**：耳で判断します。数値が PASS でも違和感があれば、手作業の Ozone に戻します
- **アウトロのトリム**：自動でやらないだけでなく、人もやりません（前節）

また、ffmpeg では手作業の Ozone に届かない部分もあると `MASTERING.md` に書いています。1つは、Drop の爆発力のような大きな抑揚で、LRA が大きい曲では手作業より 1〜1.5 LU 小さくなります。もう1つは、スマホの小さなスピーカーで低音を聞かせるための倍音の付加で、ffmpeg にはきれいに倍音を足す処理がありません。そのため、大きな抑揚や低音の演出が要となる曲は、手作業で仕上げる方針にしています。

## まとめ

RESONAL のマスタリングは、True Peak -1.5 dBTP、Integrated -9.5 ± 0.5 LUFS、48kHz / 24bit を固定値にして、`auto_master.py` で毎回そこへ着地させています。音色は固定のイコライザで整え、リミッタを4倍で掛けながら実測を繰り返して数値を合わせます。着地した後も、checklist の MASTER と MV-FILES、アップロード後の照合で、配信や動画にマスター WAV が使われているかを確かめています。
