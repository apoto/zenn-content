title: "MV④ レンダー・検査・配信・レビュー"
---

この章では、組み上がった MV をレンダーしてから、機械の検査を通し、Slack に送って僕がレビューし、承認するまでの流れを説明します。

## 後半の工程の全体像

MV のプロジェクトには、番号付きのスクリプト（番号ハーネス）が入っています。前半の 01〜03・06 は第9章と第10章で説明したので、この章では後半を扱います。

| # | スクリプト | 役割 |
|---|---|---|
| 04 | `04_render.sh` | 本編・ショート・サムネイルを書き出す |
| 07 | `07_verify.sh` | 壊れていないか、クレジットが入っているかを検査する |
| 05 | `05_deliver_slack.sh` | Slack に軽量版を送る |
| — | `run_mv.sh` | 04 → 07 → 05 を1本で実行する |

番号と実行順は一致していません。実行する順番は `run_mv.sh` の中で決めています。

そのあと、AI が `mv_selfcheck.sh` でセルフ検品をして、僕がスマホで動画を見てレビューします。

## 04_render.sh：3つを書き出して、尺を確かめる

`04_render.sh` は、第11章で説明した3つのコンポジションを、曲フォルダに決まった名前で書き出します。

| ファイル | 中身 |
|---|---|
| `<曲名>.mp4` | 本編（16:9） |
| `<曲名> (Short).mp4` | ショート（9:16） |
| `thumbnail.jpg` | サムネイル |

このスクリプトでは、レンダーのたびに出力を確かめています。Remotion は、素材の読み込みに失敗したときなどに、終了コード 0（成功）を返すことがあるためです。

```bash:projects/mv-template/tools/04_render.sh
need() {
  local f="$1" min="$2"
  [ -s "$f" ] || { echo "[NG] 出来ていない: $f" >&2; exit 4; }
  local d; d="$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$f" 2>/dev/null || echo 0)"
  awk -v d="$d" -v m="$min" 'BEGIN{ if (d+0 < m+0) exit 1 }' \
    || { echo "[NG] 尺が短すぎる: $f (${d}s < ${min}s)＝レンダーが途中で落ちている" >&2; exit 4; }
}
echo "=== ShortVideo ==="; npx remotion render ShortVideo "$SONG/${TITLE} (Short).mp4" --log=error
need "$SONG/${TITLE} (Short).mp4" 10
echo "=== LyricVideo ==="; npx remotion render LyricVideo "$SONG/${TITLE}.mp4" --log=error
need "$SONG/${TITLE}.mp4" 60
```

`need` は、ファイルが空でないことと、ffprobe で測った尺がショートは10秒以上、本編は60秒以上あることを確かめます。満たさなければ終了コード 4 で止まります。

## 07_verify.sh：配信する前に、壊れていないか確かめる

`07_verify.sh` は、書き出した動画が壊れていないかを検査するスクリプトです。

きっかけは、Static Hazard を作っていたときの事故です。パソコンのディスクの空きが足りなくなり、Remotion がエラーを出さずに正常終了したまま、前半がデコードできない mp4 を書き出していました。サムネイルや後半の静止画を見ても気づけない壊れ方でした。同じ検査を Cotton Overkill の動画にかけるとエラーは0件だったので、リグではなく環境の問題だと切り分けられました。

検査の中身は次の5つです。

| # | 検査 | 落ちたとき |
|---|---|---|
| 1 | 本編・ショート・サムネイルが存在する | 止まる |
| 2 | 本編とショートを最後までデコードして、エラーが0行 | 止まる |
| 3 | 本編の5か所（3秒・1/4・1/2・3/4・終わり4秒前）で1フレームを取り出せる | 止まる |
| 4 | 0.5秒以上の黒い区間がない | 警告のみ（意図した暗転もあるため） |
| 5 | クレジット3点の文言がある（第11章の `check-mv-credits.sh`） | 止まる |

```bash:projects/mv-template/tools/07_verify.sh
for f in "$MAIN" "$SHORT"; do
  n="$(ffmpeg -v error -i "$f" -f null - 2>&1 | wc -l | tr -d ' ')"
  [ "$n" = "0" ] && echo "[OK] デコード: $(basename "$f")" || { echo "[NG] デコードエラー ${n}行: $f" >&2; fail=1; }
done

DUR="$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$MAIN" | cut -d. -f1)"
for t in 3 $((DUR/4)) $((DUR/2)) $((DUR*3/4)) $((DUR-4)); do
  ffmpeg -v error -ss "$t" -i "$MAIN" -frames:v 1 -y /tmp/_v7.png 2>/dev/null \
    || { echo "[NG] ${t}s がデコードできない" >&2; fail=1; }
done
```

1つでも落ちると、最後に「検査に落ちた＝配信しない」と出して終了コード 1 で止まります。

## 05_deliver_slack.sh：Slack に軽量版を送る

`05_deliver_slack.sh` は、リポジトリ共通の `deliver_slack.sh` を呼ぶだけの薄いラッパーです。本編・ショート・サムネイルを、曲ごとの Slack スレッドにアップロードします。スレッドの識別子は曲の `release.json` に保存してあるので、同じ曲の動画は同じスレッドに並びます。

動画は、長辺 720p の軽量版に変換してから送ります。確認は軽量版で足りますし、数百MBの原本は Slack の中で再生できず、「動画が見当たらない」状態になったためです。

また、アップロードは次の2点を確かめてから成功としています。

- アップロード本体（PUT）の HTTP ステータスが 200 か
- 実際にスレッドにファイルが載ったか（API が `ok: true` を返しても、スレッドを読み直して確かめる）

1つ目は、`[OK]` と表示されたのにスレッドに動画が載っていなかったことがあって足した確認です。

## run_mv.sh：レンダー・検査・配信を1本で走らせる

`run_mv.sh` は、04・07・05 を順に呼ぶだけのスクリプトです。

```bash:projects/mv-template/tools/run_mv.sh
"$PROJ/tools/04_render.sh" "$PROJ" "$SONG"
"$PROJ/tools/07_verify.sh" "$SONG" "$PROJ"
"$PROJ/tools/05_deliver_slack.sh" "$TEXT" "$TS" \
  "$SONG/${TITLE}.mp4" "$SONG/${TITLE} (Short).mp4" "$SONG/thumbnail.jpg"
```

1本にしている理由は、レンダーに1時間近くかかるためです。04 と 05 が別のコマンドだと、レンダーが終わったことに誰も気づかず、そこで止まってしまうことが実際にありました。完了を人が見張らなくて済むように、最後まで繋いで走らせています。

スクリプトは `set -eu` で書いているので、07 が失敗すると 05 は実行されません。Heat Shock では、1往復目の直しのレンダー中にブラウザのタブが落ち、検査の前で止まりました。このとき、ショートだけが新しい、ちぐはぐな組み合わせの動画は Slack に送られませんでした。

また、04 の前に、Remotion が中間ファイルを書く場所（`TMPDIR`）の空きが 5GB 以上あるかを確かめています。以前は根拠のない 15GB にしていましたが、ある曲の実測で作業領域のピークが 0.7GB だったので、余裕を見て 5GB に下げました。

なお、ハーネスのスクリプトは `set -o pipefail` を使っていません。そのため、`run_mv.sh ... | tail` のようにパイプで繋いで実行すると、終了コードが `tail` のものになり、失敗を成功と読んでしまいます。実際にこれでレンダーの失敗を完走と読み違えたことがあり、今は「検証したい処理はパイプで繋がない」を CLAUDE.md の運用ルールにしています。

## mv_selfcheck.sh：観る前の準備を機械でやる

配信と並行して、AI がセルフ検品をします。その準備をするのが `mv_selfcheck.sh` で、曲フォルダの `selfcheck/` に次のものを書き出します。

![Heat Shock のコンタクトシート。曲全体から24点を等間隔に抜き出して並べる](/images/resonal-pipeline/selfcheck-heat-shock.jpg)
*Heat Shock のコンタクトシート。曲全体から24点を等間隔に抜き出して並べる*

| 出力 | 中身 | 何を観るためか |
|---|---|---|
| `contact-sheet.jpg` | 本編を24等分した点のタイル | 全体の流れ・接続・落差 |
| `main-*.jpg` | 本編のフル解像度12枚（2・5・8秒＋10%刻み9枚） | 可読性・光・奥行き。冒頭3枚はクレジット |
| `short-*.jpg` | ショートの6枚 | スマホでの見え方 |
| `measure.txt` | 黒い区間・区間ごとの動き・音量 | 目で見て気づけない事故 |

フレームを取り出す点を固定しているのは、AI が勘で選んだ点だけを見て、2回見誤ったためです。

`measure.txt` の「区間ごとの動き」は、本編の20か所で1秒離れた2枚を比べ、変化した画素の割合を出したものです。ある曲で、止めたかった締めの区間が 45.0%、動かしたかったラスサビが 2.2% と、設計と逆になっていたのに、コンタクトシートでは気づけなかったことから足しました。Heat Shock の測定は次のようになりました。

```text:260923_Heat Shock/selfcheck/measure.txt
    59.8s  変化   6.4%  最大差 168
    70.9s  変化   3.4%  最大差 208
    81.9s  変化  33.8%  最大差 208
    93.0s  変化   1.2%  最大差 255
```

81.9秒の 33.8% は、中タイトルが陽炎で溶けて彩瀬??に入れ替わる区間で、意図した動きです。

AI は Slack の報告にもこの数字を書くので、僕のレビューも数字で返すことがあります。Heat Shock では、陽炎の強さについて「陽炎の強さは10%以下で調整しながら、彩瀬の表情差分で表現するといい」と伝えました。この10%は、AI が報告した動きの割合のことです。

### 8つの観点で OK / NG を書く

フレームを観て判定する部分は、AI の仕事として残しています。スクリプトは `MV-SELFCHECK.md` の雛形を作り、AI は次の8つの観点に OK か NG と、根拠にしたフレームを書きます。

| # | 観点 |
|---|---|
| 1 | 意図一致（企画や演出の狙いが画に出ているか） |
| 2 | 可読性（歌詞を読める時間とサイズ） |
| 3 | 音楽同期（Drop やキメと画の打点） |
| 4 | 接続（シーン間の動き・色・意味の繋がり） |
| 5 | 奥行き（前景・被写体・背景の3層） |
| 6 | モーション（緩急。`measure.txt` の動きを見る） |
| 7 | 光（光源の一貫性・黒つぶれ・白飛び） |
| 8 | 独自性（この曲だけの1点があるか） |

NG は「どのファイルのどの値をどう直すか」まで書き、直して再レンダーしたら、下の「NG の対応記録」に1行ずつ残します。

## セルフ検品と納品物を機械で検査する

セルフ検品を書いたかどうかは、リリース用のチェックリスト（`checklist.js`）の `MV-SELFCHECK` という項目が検査します。

```js:release/checklist.js
const sc = fs.statSync(scPath).mtimeMs;
for (const f of [d.main, d.short]) {
  const p = path.join(ctx.dir, f);
  if (fs.existsSync(p) && sc < fs.statSync(p).mtimeMs)
    return `MV-SELFCHECK.md が ${f} のレンダーより古い（再レンダー後は mv_selfcheck.sh から検品し直す）`;
}
```

`MV-SELFCHECK.md` の更新日時が、本編やショートの動画より古ければ通しません。古い検品のまま、新しくレンダーした動画を通さないためです。あわせて、8つの観点の名前がそろっているか、表の判定欄に OK / NG が8つ入っているか、NG があるなら対応記録が空でないかも確かめます。

もう1つの `MV-FILES` という項目は、納品物そのものを検査します。主な内容は次のとおりです。

- 本編とショートにデコードエラーがない
- 本編の音量がマスタリング済みの音源と 0.8 LUFS 以内で一致する
- 本編の尺がマスタリング済みの音源と2秒以内で一致する
- ショートが縦長で、サムネイルが16:9・幅1280px以上
- 曲フォルダに、規約名以外のショートの mp4 が置かれていない
- クレジット3点の文言がある

```js:release/checklist.js
const mm = ctx.loudness(mp);
const vm = ctx.loudness(path.join(ctx.dir, d.main));
if (mm && vm && Math.abs(mm.lufs - vm.lufs) > 0.8)
  return `本編の音がマスターと違う（本編 ${vm.lufs} / master ${mm.lufs} LUFS）＝仮組み音源でレンダーした疑い`;
```

音を実測で比べているのは、設定ファイルの音源名が当てにならないためです。第8章で説明したマスタリング済みの音源でレビューに出す決まりなので、仮の音源のままレンダーしていれば、音量の差でここに引っかかります。

## スマホでレビューして、往復する

ここまで終わると、僕の番です。MV のレビューは、僕が判断する3か所のうちの3つ目で、チェックリストでも `MV-REVIEW` という人の項目になっています。

僕は、Slack の曲のスレッドに届いた軽量版の動画をスマホで見て、気になった点を時刻つきで返します。AI が直して再レンダーすると、`run_mv.sh` が同じスレッドにまた送ってくるので、それを見て次の指摘を返します。

この往復は1回で終わらないことが多いです。Heat Shock は5往復しました。各回の指摘の一部は次のとおりです。

| 往復 | 僕の指摘（抜粋） |
|---|---|
| 1 | 「木のベンチ」「上の段」など歌詞が重なって見える／「水風呂がちょっと怖い。頭だけ見えていて水死体を想起させる」 |
| 2 | 「砂時計がうまく動いていない」／「下手にアングルを切るより、ずっと引きのまま中央の彩瀬をじわじわ小さく」 |
| 3 | 「0:40・1:04・1:16 で、徐々に汗の量を増やしたり、より熱い様子にしたり、画面全体に陽炎をかけたり、変化をつけたい」 |
| 4 | 「陽炎の強い描写が強すぎる。彩瀬の顔が歪みすぎ」 |
| 5 | 「1:07からのクレジットが見えづらい」／「2:42 一瞬だけ砂時計と『耳の後ろが』が同時に出てる」 |

1往復目の歌詞の重なりは、秒のデータでは重なっていないのに、レンダーで開始と終了を別々にフレームへ丸めたために、1フレーム食い込んでいたものでした（11か所）。AI は秒で重なりを検査して「重なりなし」と報告していたので、検査の側がフレームを見ていなかったことになります。直し方は、終わりのフレームを次の行の開始フレームで打ち切る式に変えるものでした。

5往復目の「2:42」も同じ種類の原因で、歌詞はフレームに丸めて表示しているのに、背景の絵の区間は秒のまま比べていました。このときは描画と検査の両方をフレームに揃えています。

このように、スマホで見て気づいた点を返すと、AI が原因まで掘って直し、同じ検査を足していく、という流れになっています。

## 承認したら、日付を記録する

僕が OK を出すと、AI は曲の `release.json` に承認した日付を書きます。Heat Shock では、5往復目の版を見て「完成！」と返しました。

```json:260923_Heat Shock/release.json
  "mv_approved_at": "2026-09-24",
```

チェックリストの `MV-REVIEW` は、この値があるかだけを見ています。

```js:release/checklist.js
check: (ctx) => (ctx.rj.mv_approved_at ? true
  : 'apoto のレビュー未通過（本編＋ショートを Slack に配信して待つ）'),
```

会話の中で「完成」と言っただけでは、記録に残りません。値として書いておくことで、`next.sh` が次の工程（リリースの準備）に進めるようになります。

## まとめ

MV は `run_mv.sh` で、レンダー（04）・検査（07）・配信（05）を1本で走らせ、検査に落ちたら Slack には送りません。配信と並行して、AI が `mv_selfcheck.sh` で取り出したフレームと測定値を観て8つの観点で検品し、チェックリストがその鮮度と納品物の音・尺を確かめます。僕はスマホで動画を見て指摘を返し、往復のあと OK を出すと `mv_approved_at` に日付が記録されます。
