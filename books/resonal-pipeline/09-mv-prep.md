この章では、ミュージックビデオ制作の前半として、プロジェクトの作成から、歌詞の文字起こし・拍の測定・素材の用意までを説明します。展示では「動画はどうやって作っているのか」という質問を多くいただいたので、ミュージックビデオの話は第9章から第12章までの4章に分けて書きます。

## MV制作の全体像

RESONAL のミュージックビデオ（以下 MV）は、Remotion で作っています。Remotion は、React のコンポーネントとして画面を書き、それを1フレームずつ書き出して動画にするライブラリです。

曲ごとに `projects/<曲の略称>-mv/` というプロジェクトを1つ作り、その中の `tools/` に入っている番号付きのスクリプトで工程を進めます。

| # | スクリプト | 役割 |
|---|---|---|
| 01 | `01_transcribe.sh` | 音源を文字起こしして、歌詞のタイミングを取る |
| 02 | `02_energy.py` / `02_estimate_beats.py` | 映像を動かすための信号 `energy.json` と、拍の位置を作る |
| 03 | `03_prep_material.sh` / `03b_prep_cover.sh` / `03c_cutout_fg.sh` | 素材を整える（動画素材のループ化 / カバー画像から背景 / キャラの切り抜き） |
| 06 | `06_build_lyrics.py` | 歌詞の正本とタイミングから `lyrics.json` を作る |
| 04 | `04_render.sh` | 本編・ショート・サムネイルを書き出す |
| 07 | `07_verify.sh` | 書き出した動画が壊れていないか、クレジットが入っているかを検査する |
| 05 | `05_deliver_slack.sh` | Slack に送る |
| — | `run_mv.sh` | 04 → 07 → 05 を1本で実行する |

実行する順番は次のとおりです。番号の順ではなく、06 は 04 の前、07 は 04 と 05 の間に入ります。

1. `01_transcribe.sh`（文字起こし）
2. `02_energy.py`（映像を動かす信号）と拍の測定
3. `03b_prep_cover.sh` など（素材）
4. `06_build_lyrics.py`（歌詞の秒を決める）
5. `run_mv.sh`（04 レンダー → 07 検査 → 05 配信）

この章では 01〜03 を、第10章では 06 を説明します。Remotion での画面の組み立ては第11章、04・07・05 と `run_mv.sh` は第12章で説明します。

なお、MV の作り方を曲ごとに変えてきたので、プロジェクトによって入っているスクリプトに差があります。例えば `02_energy.py`・`03_prep_material.sh`・`06_build_lyrics.py` は、最新のテンプレート（`projects/mv-template`）には無く、それを使うスタイルの曲のプロジェクトにだけ入っています。

## 自前のコマンドを書かず、番号スクリプトに乗る

MV の制作では、AI が同じ処理をその場で書き直さず、プロジェクトに入っている番号スクリプトを呼ぶように決めています。`CLAUDE.md` にも「同じことをする自前のコマンドを書かない」と書いています。

このルールができたのは、実際に失敗したためです。ある曲の MV で、AI が番号スクリプトを一度も使わずに、文字起こしからレンダーまでを手打ちのコマンドで作り直したことがありました。その結果、`06_build_lyrics.py` が持っていた「行の長さからフォントサイズを計算する」処理が使われず、歌詞が画面の外にはみ出したまま本番のレンダーまで進みました。レンダーには1時間ほどかかるので、それをやり直すことになりました。

原因として記録しているのは次の2つです。

- プロジェクトをコピーした直後に、手順の正本である `README.md` を読まなかった
- 「次にやること」を返す `next.sh` の指示文が、番号スクリプトを名指ししていなかった

2つ目は、指示文を「`01_transcribe.sh` → `02_energy.py` → … → `run_mv.sh`」とスクリプト名で書く形に直しました。この失敗では、スクリプトが既にあっても、AI がそれを知る経路が無かったために使われませんでした。そのため、ルールの文章を増やすのではなく、AI が毎回読む指示の中にスクリプト名を直接書くようにしています。

## new_mv_project.sh でプロジェクトを作る

プロジェクトは手でコピーせず、`new_mv_project.sh` で作ります。

```bash
./tools/new_mv_project.sh "<曲フォルダ>" <曲の略称>-mv [--from <コピー元>]
```

このコマンドは次の4つを行います。

1. コピー元（既定は `projects/mv-template`）から、`node_modules` などを除いてコピーする
2. 曲の `release.json` に `mv_project` として、プロジェクト名を記録する
3. 番号スクリプトが揃っているかを検査し、欠けていれば止まる
4. コピー元の曲名が `src/` に残っていないかを探して表示する

3つ目の検査は次の部分です。

```sh:tools/new_mv_project.sh
fail=0
for f in README.md tools/04_render.sh tools/07_verify.sh tools/05_deliver_slack.sh tools/run_mv.sh; do
  if [ -e "$PROJ/$f" ]; then echo "[OK] $f"; else echo "[NG] 無い: $f" >&2; fail=1; fi
done
```

この検査を入れたのは、Whiteout の MV が、番号スクリプトが1本も無いプロジェクトのまま最後まで進んでしまったためです。また、4つ目は、別の曲のプロジェクトをコピー元にしたときに、ショートの帯のタイトルやサムネイルの文字が前の曲のまま残っていたことがあったので追加しました。どちらもレンダーは通ってしまうので、目で見るまで気付けませんでした。

コマンドの最後には、プロジェクトの `README.md`（手順の正本）を読むよう表示します。

## DIRECTION.md — 実尺タイムラインとカット別演出表

スクリプトを動かす前に、AI が `DIRECTION.md`（演出の設計書）を書きます。第6章で決めた映像の方向性を、実際の音源の秒に落としたものです。

中心になるのは次の2つの表です。

- **実尺タイムライン**：実際の音源を測って、どの秒からどの区間（イントロ・Aメロ・サビなど）が始まるかを書いた表
- **カット別演出表**：区間ごとに、役割・カットの並び・カメラとつなぎ方・歌詞の出し方・参考にした演出記録を書いた表

例えば Dive Reflex の `DIRECTION.md` は、次のように書いています。

```markdown:260925_Dive Reflex/DIRECTION.md
| # | 区間 | 秒 | 音（実測） | 場所 |
|---|---|---|---|---|
| S0 | Intro | 0.0–10.7 | energy 0＝SFX と息だけ | 水上 |
| S1 | A1 | 10.7–32.0 | 低（0.0–0.2）・talk-sing | 水上 |
| S2 | B1 | 32.0–44.0 | 中（0.3）→ **42.0–43.9 で無音の穴**（息を止める） | 水上 → 着水 |
| S3 | Chorus1 / Drop | **44.0**–62.5 | 高（0.8–0.94）。44.0 が drop onset | 水中（浅い） |
```

```markdown:260925_Dive Reflex/DIRECTION.md
| 区間 | 役割 | 並び | カメラ・つなぎ | タイポ | 使用レコード |
|---|---|---|---|---|---|
| Intro 0:00 | マスターショット | E-L8 海のドリフト（夕焼け・対岸の町） | ほぼ固定のドリフト。彩瀬はまだ出さない（留め） | クレジット3点 | records/cut-entry-drift.md, records/negative-space.md |
| A1 0:10.7 | 状況（客観→主観） | E夕日の道3 → K1桟橋に座る-L3 → K10ラジオ-C2 → K1c顔（髪ゴムを手首へ）-C2 → E水面すれすれ3 → K1bつま先-C2 | 場所→人→象徴（ラジオ）→寄り。引きは長く・寄りは短く | 下帯 | records/single-set-multicam.md, records/breathing-idle.md |
| B1 0:31.4 | 助走（間隔を詰める 2→3→2→1→1） | K1-M2 → E入り江3 → K2d水面から見上げて屈む-M2 → E足元の水面へ寄る目線1 → K2e見上げて跳ぶ笑顔-L1 | 見上げる→見下ろす→見上げるの切り返し・初動で切る | 下帯 | records/push-in.md, records/pov-shot.md, records/match-cut.md |
| Chorus1 0:43.6 | 結論（ベース画=光の筋） | E着水直後の見上げ2(hit) → K3胸に手を当てて聞く-L2 → E光の筋3 → K3-C1 → E底を滑る2 → K3-M1 → K4泡を吐いて笑う-C2 → E水面へ1 | 水面の越境は中抜き。編集は速く・芝居は静か | サビ頭のタイトル中央 | records/light-flood-wipe.md, records/god-rays.md, records/jump-cut.md |
```

カット別演出表の「並び」の E は3Dの環境だけのカット、K は2Dの彩瀬の1枚絵のカットです。L/M/C/X は画面のサイズ（引きから超寄りまで）、数字はカットの長さを小節で表しています。

「実尺」と呼ぶのは、企画時に想定した構成ではなく、できあがった音源で測った秒を使うためです。Suno は指示どおりの構成で作るとは限らず、この曲でも、最後に歌詞に無い「Dive Reflex 空の方へ」という一節を Suno が足していて、曲は232.1秒まで続いていました。

`DIRECTION.md` も中身を検査しています。各表の文字数、「使用レコード」に書いた演出記録が実在するか、シーンごとに変える軸が書かれているかを `checklist.js` で確認します。

## 01 文字起こし — Whisper で歌詞の秒を取る

最初に、音源を Whisper で文字起こしします。Whisper は OpenAI が公開している音声認識モデルで、ローカルで動かせます。RESONAL では openai-whisper の CLI を、medium モデルで使っています。

```sh:projects/mv-template/tools/01_transcribe.sh
ffmpeg -y -i "$AUDIO" -ar 16000 -ac 1 "$OUT/audio_16k.wav" -loglevel error
echo "[whisper] transcribing (medium, language=$LANG_CODE)…"
whisper "$OUT/audio_16k.wav" --language "$LANG_CODE" --model medium --word_timestamps True \
  --output_format json --output_dir "$OUT" --fp16 False
# ★成果物を検査してから成功を名乗る（whisper はモデルDLに失敗しても 0 を返すことがある）
[ -s "$OUT/audio_16k.json" ] || { echo "[NG] $OUT/audio_16k.json が出来ていない（whisper が落ちた）" >&2; exit 4; }
```

ffmpeg で音源を 16kHz・モノラルの wav に変換してから Whisper に渡し、`--word_timestamps True` で単語ごとの開始秒も出します。言語は曲の `release.json` の `lyrics_lang` から決めています。言語を自動で決めるようにしたのは、英語詞の曲を日本語として文字起こしして、単語のタイミングが崩れたことがあったためです。

最後の1行は、出力ファイルが空でないかを確かめる検査です。Whisper は、モデルのダウンロードに失敗したときでも終了コード 0 を返すことがあります。終了コードだけを見ると成功に見えるので、成果物そのものを見て判断しています（この考え方は第16章で詳しく書きます）。

## 02 energy.json と拍

### energy.json — 映像を動かす2つの信号

`02_energy.py` は、音源から映像を動かすための信号を、1フレームごとに作ります。出力の `energy.json` には `sec` と `hit` の2つの配列が入っています。

| 信号 | 意味 | 動き方 | 主な使い道 |
|---|---|---|---|
| `sec` | 区間の強さ | ゆっくり変わる。サビで高く、Aメロや落ちサビで低い | 明るさ・彩度など |
| `hit` | 打点 | 速く変わる。キックやスネアの立ち上がりで跳ねる | ズームの打ち込みなど |

```python:projects/cotton-overkill-ricochet-mv/tools/02_energy.py
    # 下 8% / 上 96% で伸ばす（落ちサビの静けさを 0 付近に落とし、Drop を 1 に張らせる）
    sec = normalize(smooth, 0.08, 0.96)

    # ---- ③ hit = RMS の正の差分（オンセット）→ 正規化 → ピークホールド減衰 ----
    diff = [0.0]
    for f in range(1, frames):
        diff.append(max(0.0, rms[f] - rms[f - 1]))
    hit_raw = normalize(diff, 0.55, 0.995)
    hit: list[float] = []
    prev = 0.0
    decay = 0.62  # 1フレームごとの減衰（打点を数フレーム保たせて見える打点にする）
    for v in hit_raw:
        cur = max(v, prev * decay)
        hit.append(cur)
        prev = cur
```

`sec` は、1フレームごとの音量（RMS）を2.5秒の窓で平均して0〜1に伸ばしたものです。`hit` は、音量が前のフレームより上がった量（オンセット強度。オンセットは音が鳴り始める瞬間のこと）を0〜1に伸ばし、1フレームごとに0.62倍ずつ減らしたものです。減らしながら保つのは、1フレームだけの打点は画面上で見えないためです。

`energy.json` を画面でどう使うかは第11章で説明します。

### 拍 — BPM は実測し、1つの値を鵜呑みにしない

歌詞やカットを拍に合わせるには、BPM（1分あたりの拍の数）と、最初の拍の位置が必要です。ここで守っているのは、発注した BPM ではなく、できあがった音源から測った値を使うことです。

例えば、ある曲では Suno に BPM 122 で発注しましたが、実際の音源は 126.05 BPM でした。発注値のまま跳ねる動きを組んだところ、曲と動きがずれていました。また、Bubble Trouble は曲の途中で 136.2 から 138.4 BPM へ少しずつ速くなっていて、1つの BPM では曲の後半でずれました。

テンプレートに入っている `02_estimate_beats.py` は、音量の変化の自己相関から BPM を1つだけ出すスクリプトです。しかし、上の BPM 126.05 の曲ではこのスクリプトが 123.0 を返していました。そのため今は、次の手順で区間ごとに測る `tools/estimate_tempo_sections.py` で確かめています。

1. 音源の低い周波数を重く見たスペクトルの変化量（キックが鳴った瞬間に大きくなる値）を作る
2. 区間ごとに、BPM と最初の拍の位置の組み合わせを総当たりし、拍の位置で値が大きくなる組を選ぶ
3. 高い周波数（ハイハットやクラップ）でも同じ推定をして、BPM が 0.3 以内で一致するかを確かめる

Dive Reflex では、発注 174 BPM に対して、実測は 177.6 BPM から 180.2 BPM へ少しずつ速くなっていて、最初の拍は 0.335 秒でした。1つの BPM では拍が合わないため、区間ごとの値を `tempo.json` に書き、`DIRECTION.md` の先頭にもそのことを書いています。以降の工程ではこの値を使います。

## 03 素材 — 背景・切り抜き・ループ動画

### カバー画像から背景を作る

`03b_prep_cover.sh` は、曲のカバー画像から、本編用（16:9）とショート用（9:16）の背景を作ります。

```sh:projects/mv-template/tools/03b_prep_cover.sh
ffmpeg -y -i "$IN" -vf "scale=1920:1080:force_original_aspect_ratio=increase,crop=1920:1080" "$PUB/bg.png" -loglevel error
ffmpeg -y -i "$IN" -vf "crop=ih*9/16:ih:(iw-ih*9/16)/2:0,scale=1080:1920" "$PUB/bg_vertical.png" -loglevel error
```

### キャラを切り抜く

`03c_cutout_fg.sh` は、カバー画像から彩瀬??を切り抜きます。切り抜きには rembg を、アニメ絵向けの `isnet-anime` モデルで使っています。rembg は画像の背景を取り除く Python のライブラリで、ローカルで無料で動きます。

切り抜いた画像は、背景と同じ切り取り方で 16:9 と 9:16 に書き出します。そうすることで、背景の上に置いたときにキャラの位置がぴったり重なります。前後を分けておくと、キャラの後ろに光を置いたり、キャラの手前に文字を通したりできます。

### 静止画を短いループ動画にする

静止画を少しだけ動かしたいときは、Kling で5秒ほどの動画にします。Kling は画像や文章から動画を作るサービスで、公式の MCP サーバーがあるので、Claude Code から直接呼び出しています。

動画にするときは、大きな動きは付けません。瞬きや呼吸、髪の揺れ、ネオンの明滅のように、元の状態に戻る小さな動きだけを指示します。プロンプトの型は Skill `kling-living-loop` にまとめています。

ループさせる方法は2つあります。

| 方法 | やり方 | 向いている動き |
|---|---|---|
| 始点と終点を揃える | Kling の `first_image` と `tail_image` に同じ画像を指定し、「最後に元の状態に戻る」と書く | 粒子が上に流れるなど、一方向の動きを含むもの |
| 往復再生 | 生成した動画を、順再生と逆再生でつなぐ | 明滅や呼吸など、往復するだけの動き |

往復再生は、一方向の動きに使うと逆再生の部分で粒子が逆に流れて見えます。また、折り返しで動きに違和感が出ることもあり、僕が「ピンポンループは基本的に使えません」と伝えてからは、始点と終点を揃える方法を基本にしています。なお、Kling の 720p では `tail_image` が使えないため、この方法では 1080p で生成します。

以前のプロジェクトでは、`03_prep_material.sh` で Kling の動画の下端を8%クロップしてウォーターマークを除き、16:9 と 9:16 に切り出して往復再生にしていました。

### 画像素材は ChatGPT で作る

カバー画像以外の画像素材（キャラの別ポーズや背景など）は、ChatGPT の画像生成で作っています。

使ってみて分かったのは、参照画像を付けないほうが指示どおりに出やすいことです。キャラの見た目を揃えるために過去のポスター画像を参照に付けたところ、参照をそのまま写したような絵になり、構図の指示が無視され、`no text` と書いたのに文字が入り、縦横比も参照と同じになりました。参照を外してキャラの特徴をプロンプト本文に書くと、1回で指示どおりに出ました。そのため今は参照画像を付けないことを基本にしています。

## まとめ

MV は、曲ごとのプロジェクトに入っている番号付きのスクリプトで作っています。プロジェクトは `new_mv_project.sh` で作り、スクリプトが揃っているかを最初に検査します。そのうえで、`DIRECTION.md` に実尺の秒で演出を書き、Whisper で歌詞のタイミングを取り、`energy.json` と実測した拍を用意し、背景・切り抜き・ループ動画の素材を整えます。次章では、こうして取った秒を使って歌詞を画面に出すタイミングを決める `06_build_lyrics.py` を説明します。
