---
title: "リリース — コマンド1つで6つを予約する"
---

この章では、ミュージックビデオが完成したあとのリリース作業を、1つのコマンドでどう進めているかを説明します。

## release.sh がやる6つのこと

ミュージックビデオのレビューで僕が OK を出したら、次のコマンドを1回実行します。`--date` には YouTube の公開日を渡します。

```bash
./release/release.sh "<曲フォルダ>" --date=2026-09-21
```

このコマンドは、次の6つを順に行います。

| # | 項目 | 内容 |
|---|---|---|
| ① | YouTube の公開予約 | 本編をアップロードし、公開日の19:00に公開するよう予約する |
| ② | ショートの自動公開予約 | 縦長のショート動画を非公開でアップロードし、公開日に自動で公開する処理を登録する |
| ③ | 配信サービスへの入稿 | DistroKid に入稿する。リリース日は YouTube の公開日と同じにする |
| ④ | SNS の予告 | 公開日の前夜20:00に、X と Threads へ予告を投稿するよう予約する |
| ⑤ | プレイリスト | `release.json` で選んだムード別のプレイリストに、曲を追加する（実際の反映は毎晩21:30の同期処理が行う） |
| ⑥ | ショート素材の量産 | 本編から短いクリップを切り出し、毎日のショート投稿の順番に加える |

リリースは mac mini で実行しています。理由は第3章で説明したとおり、ショートの自動公開が、アップロードしたパソコンの上で動くためです。

以前は、これらを別々のコマンドで実行していました。しかし、入口が分かれていると、どれかを実行し忘れることがありました。そこで、1つのコマンドにまとめています。

### 公開時刻は19:00に固定している

公開時刻は、次のように決めています。すでに予約済みならその時刻を使い、なければ `--date` の日付に19:00を付けます。

```js:release/release.js
let publishAt =
  (rj && rj.youtube && rj.youtube.publish_at) ||
  // 既定は 19:00 JST（2026-08-15 apoto確定。朝7時＝通勤帯から、視聴のゴールデンタイムへ移行）。
  // 変えるときは release/README.md と監査ジョブ(com.resonal.release-audit)の時刻もセットで見直す。
  (flags.date ? `${flags.date}T19:00:00+09:00` : null) ||
  (fs.existsSync(metaPath) ? readJson(metaPath).publishAt : null);
```

以前は朝7時に公開していましたが、2026年8月に19時へ変えました。コメントにあるとおり、夜の監査（第14章）の時刻もこの19時を前提に決めているので、変えるときはあわせて見直します。

## 1曲のリリースの時間の流れ

1曲のリリースは、次の順に進みます。

| いつ | 何が起きるか |
|---|---|
| ミュージックビデオの完成日 | `release.sh` を実行する（①〜⑥） |
| 公開日の前夜20:00 | X と Threads に予告が投稿される |
| 公開日の19:00 | YouTube で本編が公開される |
| 公開日の19:10 | ショートの公開、X での告知などが自動で動く |
| 公開日の20:00 | 毎晩の監査が、予定どおりに進んだかを確かめる（第14章） |

リリース日を YouTube の公開日にそろえているのは、YouTube に出した曲は配信サービスにも同じ日に出す、という方針にしているためです。

## 何度実行しても同じ結果になる

`release.sh` は、何度実行しても同じ結果になるように作っています。各項目は、実行する前に「もう済んでいるか」を確かめ、済んでいれば何もせずに次へ進みます。

例えば、配信サービスへの入稿は次のように判定しています。

```js:release/release.js
  const dspSkip = rj && (rj.dsp === 'skip' || (rj.dsp && rj.dsp.skip));
  if (rj && rj.distrokid && rj.distrokid.submitted_at) {
    mark('③ DistroKid', 'done', `入稿済み（${rj.distrokid.submitted_at}）`);
  } else if (dspSkip) {
    mark('③ DistroKid', 'skip', 'release.json dsp:skip（宣言済み）');
```

曲の記録ファイル `release.json` に入稿日が書かれていれば、入稿済みとして飛ばします。

この作りにしているので、途中で失敗したときの直し方は「同じコマンドをもう一度実行する」だけです。例えば、SNS の予告文を書き忘れて④が失敗した場合は、予告文を書いてから同じコマンドを実行します。すると、①〜③は済んでいるので飛ばされ、④から先だけが実行されます。

ただし、①の YouTube のアップロードが失敗したときは、そこで止めます。②以降は、YouTube の動画 ID を前提にしているためです。

最後に、結果を Slack に1枚のカードとして送り、`release.json` などの変更を commit して push します。

## 例外は宣言する

曲によっては、6つのうちいくつかをやらないことがあります。その場合は、`release.json` に「やらない」と書いておきます。

| 書くもの | 意味 |
|---|---|
| `"dsp": "skip"` | 配信サービスに出さない |
| `"shorts": "skip"` | ショートを作らない |
| `"shorts_farm": "skip"` | ショート素材を量産しない |
| `"playlist": "all-only"` | ムード別のプレイリストには入れない |

宣言がないまま空欄になっていると、毎晩の監査は「やり忘れ」として通知します。意図してやらないのか、忘れているのかを、ファイルを見れば区別できるようにするためです。

## ショートは5つの段階で進める

公式のショート動画は、1曲に1本だけ出します。このショートは、次の5つの段階を順に進みます。

```
none ──upload(private)──▶ uploaded ──link──▶ linked ──publish──▶ public ──comment──▶ commented
```

| 段階 | 意味 | いつ進むか |
|---|---|---|
| none | まだアップロードしていない | — |
| uploaded | 非公開でアップロードした | ミュージックビデオの完成日（`release.sh` の②） |
| linked | ショートから本編へのリンクを付けた | 公開日の19:10 |
| public | ショートを公開した | 公開日の19:10 |
| commented | ショートに投稿者コメントを付けた | 公開日の19:10 |

どの段階にいるかは、`release.json` に書かれた記録から判断します。各工程は、実際にできたことを確認できたときだけ、自分の記録（`linked_at` や `published_at` など）を書きます。

あわせて、次の3つの条件を守っているかも確かめます。

- 1曲につきショートは1本だけ
- 記録している動画 ID が、YouTube に実在する
- 本編へのリンクを確認しないまま公開していない

どれかに違反していたら、処理を進めずに止めて、僕に知らせます。

### アップロードを完成日に移した理由

以前は、公開日の自動処理が、アップロードから公開までを毎回順に実行していました。しかし2026年9月の Cotton Overkill で、公開日を変えたときに自動処理が2回登録され、同じショートが2本アップロードされました。さらに、2本とも公開されてしまいました。

アップロードは、一度実行すると取り消せない操作です。そこで、アップロードは僕が作業しているミュージックビデオの完成日に済ませておき、公開日の自動処理はリンク・公開・コメントの3つだけを行うようにしました。自動処理が2回動いても、アップロード済みであれば再びアップロードすることはありません。

## 公開日当日の自動処理

`release.sh` の②では、公開日の自動処理を launchd（macOS で決まった時刻に処理を動かす仕組み）に登録します。この処理は、本編の公開から10分後に動き、次のことを行います。

1. ショートを、今いる段階から commented まで進める
2. X で新曲を告知する（本編の動画を投稿し、スレッドに YouTube のリンクを付ける）
3. TikTok の下書きを作る
4. 結果をまとめて Slack に送る
5. 自分自身の登録を削除する（1回だけ動くようにするため）

これらの工程は、互いに独立させています。以前は、1つ目のショートの工程が失敗すると、そこで処理が終わっていました。その結果、2026年8月の Skip Intro では、本編は公開されたのに、X の告知や TikTok の下書きまで出ませんでした。いまは、ショートの工程が失敗しても2以降は実行し、最後に結果をまとめて Slack に送ります。

## release.json — 1曲の記録

`release.json` は、1曲のリリースに関する記録です。曲フォルダごとに1つあります。

公開済みの Stutter Step を例にすると、次のようになっています（配信サービスの ID は伏せています）。

```json:260905_Stutter Step/release.json
  "mv_approved_at": "2026-09-07",
  "youtube": {
    "video_id": "4tyUotQb180",
    "url": "https://www.youtube.com/watch?v=4tyUotQb180",
    "publish_at": "2026-09-21T10:00:00.000Z",
    "privacy": "scheduled",
    "uploaded_at": "2026-09-07T14:47:49.013Z"
  },
  "distrokid": {
    "submitted_at": "2026-09-07",
    "expected_live": "2026-09-21",
    "assets_ready": true,
    "album_uuid": "（伏せ字）"
  },
```

ミュージックビデオの承認、YouTube へのアップロード、配信サービスへの入稿が、同じ9月7日に済んでいます。公開は2週間後の9月21日19:00（UTC の10:00）です。

ショートの記録は次のとおりです。

```json:260905_Stutter Step/release.json
  "youtube_shorts": [
    {
      "video_id": "AJlju0zlKeY",
      "url": "https://www.youtube.com/watch?v=AJlju0zlKeY",
      "publish_at": null,
      "linked_at": "2026-09-21T10:10:52.356Z",
      "published_at": "2026-09-21T10:10:56.177Z",
      "commented_at": "2026-09-21T10:10:57.567Z"
    }
  ]
```

本編の公開から10分後に、リンク・公開・コメントの3つが数秒のうちに記録されています。

なお、`youtube.privacy` は公開後も `"scheduled"` のまま更新されません。そのため、本編が公開されたかどうかは、この値ではなく、YouTube の API で実際の状態を確かめています（第14章）。

## まとめ

リリースは、`release.sh` を1回実行して、YouTube の公開予約、ショートの自動公開予約、配信サービスへの入稿、SNS の予告、プレイリスト、ショート素材の6つを済ませます。済んだ項目は飛ばすので、失敗したときは同じコマンドをもう一度実行します。やらない項目は `release.json` に宣言し、ショートは5つの段階を記録しながら進めています。
