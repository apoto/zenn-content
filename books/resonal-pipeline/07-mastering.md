この章では、生成した音源 `audio.wav` から、配信用のマスター `<Title>.wav` を作る工程を説明します。

## マスタリングとは

マスタリングは、完成した曲の音量や音色を整えて、配信できる状態の音源に仕上げる工程です。公開版では、Sunoなどで生成したステレオの音源（`audio.wav`）を入力にして、配信とMVの両方に使う `<Title>.wav` を1つ作るところまでをマスタリングと呼んでいます。

この章で出てくる用語は、次の意味です。

- LUFS：人の耳の感じ方に合わせて測った音量の単位です。曲全体の平均をIntegratedと呼びます
- True Peak（dBTP）：サンプルとサンプルの間まで補って測った、本当のピークの値です
- LRA（LU）：曲の中で、静かな部分と大きな部分の音量がどれくらい離れているかを表す値です

## 目標の数値はセットアップで選ぶ

目標の数値は、セットアップ（「はじめ方とセットアップ」の章）で答える「音の大きさ」の質問で決まります。選べるのは次の2つのプリセットです。

| preset | Integrated | True Peak | 向き |
|---|---|---|---|
| `streaming`（既定） | -14 LUFS | -1.0 dBTP | 配信サービスの基準音量。ダイナミクスが残る |
| `loud` | -9.5 LUFS | -1.5 dBTP | 音圧を出したいジャンル（EDMなど） |

セットアップの質問には「迷ったらstreaming」と書いています。ちなみにRESONALの曲は、`loud` と同じ -9.5 LUFS / -1.5 dBTPでマスタリングしています。True Peakを0より下に置いているのは、AACやMP3に変換したときに、エンコーダで音が割れるのを防ぐためです。

選んだ値は `workflow.config.json` の `mastering` に入ります。

```json:workflow.config.example.json
  "mastering": {
    "preset": "streaming",
    "integratedLufs": -14,
    "lufsTolerance": 0.5,
    "truePeakCeiling": -1.0,
    "sampleRate": 48000,
    "bitDepth": 24
  },
```

目標値の正本はこのファイルだけで、`auto_master.py` のコードには数値を書いていません。許容幅は ±0.5、書き出し形式は48kHz / 24bitが既定です。48kHzにしているのは、RESONALで使っているSunoの音源が48kHzで、YouTubeの動画の音声も48kHzが標準だからです。

## auto_master.pyの流れ

マスタリングの工程では、AIが次のコマンドを1回実行します。

```bash
python3 mastering/auto_master.py "songs/<曲フォルダ>/audio.wav" --promote
```

中では、次の順で処理します。

1. 入力が既にマスター済みでないかを確かめる
2. 48kHz / 24bitのWAVに1回だけ変換する
3. 固定のイコライザで音色を整える
4. ゲインとリミッタを繰り返して、目標の数値に着地させる
5. 判定して、実測レポート `MASTER-REPORT.md` を書き出す
6. 判定がPASSなら、`--promote` で `<Title>.wav` に昇格する

### 二重マスターを防いでから、48kHz / 24bitにする

最初に、入力のIntegratedを測ります。-11 LUFSより大きい場合は、既にマスター済みの音源とみなして止めます。マスター済みの音源にもう一度リミッタを掛けると、音を二重に潰すことになるためです。次に、入力を48kHz / 24bitのWAVに変換します。入力がMP3でも変換はここで1回だけです。

### 音色は、固定のイコライザで整える

トーンの整形は「Houseテンプレート」と呼んでいる処理で、どの曲にも同じイコライザのカーブを当てます。別の曲に音色を寄せる処理ではありません。

```python:mastering/auto_master.py
    chain = [
        "highpass=f=28",                                              # sub の下だけ落とす（sub は残す）
        f"lowshelf=f=100:g={k['low']:.2f}",
        f"equalizer=f=550:width_type=q:w=0.7:g={k['scoop']:.2f}",
        f"equalizer=f=3300:width_type=q:w=1.2:g={k['presence']:.2f}",
        f"highshelf=f=7000:g={k['shelf7k']:.2f}",
        f"equalizer=f=8500:width_type=q:w=1.0:g={k['harsh']:.2f}",
        f"equalizer=f=12000:width_type=q:w=1.0:g={k['air']:.2f}",
    ]
```

上から、28Hzより下を落とし、100Hzの低域を足し、550Hzの箱鳴りを削り、3.3kHzと7kHzから上を少し上げ、8.5kHzのきつく聞こえる帯域を抑え、12kHzを少しだけ足します。RESONALで手作業のマスタリングをしていたころ、毎回ほぼ同じ処理をしていたので、それをテンプレートにしたものです。

各帯域の量は、`bright` / `neutral`（既定） / `sub-driven` / `dark` の4つのプロファイルで切り替えます。例えば `neutral` は、100Hzを +2.5dB、550Hzを -1.2dB、7kHzから上を +1.5dB、8.5kHzを -2.0dBにします。プロファイルは、元の音源の明るさや低音の量に合わせて選びます。

### 着地ループで、目標の数値に合わせる

音色を整えた後は、ゲインとリミッタで目標の数値に合わせます。1周ごとに、ゲインを掛け、サンプルレートを4倍に上げてリミッタ（ffmpegの `alimiter`）を掛け、48kHzに戻してからebur128で実測します。4倍に上げるのは、サンプルとサンプルの間のピークを捉えるためです。RESONALで測ったときは、48kHzのまま天井を -1.7に抑えてもTrue Peakは -0.8 dBTPまで漏れ、4倍で掛けると -1.6に収まりました。

実測した後は、次のように判断します。

```python:mastering/auto_master.py
        tp_over = (m["TP"] if m["TP"] is not None else -99) - TARGET_TP
        if tp_over > 0.0:
            ceiling -= tp_over + 0.05
            continue
        di = TARGET_I - (m["I"] if m["I"] is not None else TARGET_I)
        if abs(di) > 0.15:
            gain += di
            continue
        return last
```

True Peakが上限を超えていれば、リミッタの天井を下げてやり直します。True Peakが収まっていて、Integratedが狙いから0.15より大きくずれていれば、その差だけゲインを足してやり直します。これを7周まで繰り返します。

狙いのIntegratedは、目標より0.2 dB静かめに置いています（`streaming` なら -14.2）。許容幅の静かめの側に着地させると、リミッタで削る量が減り、LRAが残るためです。RESONALの曲で試したときは、-9.4を狙うとLRAは2.5、-9.7を狙うと2.9でした。

## 判定して、MASTER-REPORT.mdに書き出す

着地した音源は、次のどれかに当てはまるとNGになります。

| NGの条件 | 意味 |
|---|---|
| True Peakが上限を超えている | 天井を守れていない |
| Integratedが目標 ±0.5の外 | 音量が目標から外れている |
| サンプルレート・ビット深度が設定と違う | 書き出し形式が違う |
| LRAが入力より1.0より多く減り、かつ3.0未満 | 潰しすぎ |
| Flat factorが1.0を超えている | 波形の頭が平らに切れている（クリップの疑い） |

LRAの条件を2つ組み合わせているのは、元のLRAが大きい曲や小さい曲を、誤ってNGにしないためです。RESONALでは、値だけで判定していたころに、元からLRAが小さい曲がNGになったことがありました。

判定の結果は、実測値や帯域ごとの音量と一緒に `MASTER-REPORT.md` に書き出します。`--promote` を付けていると、判定がPASSのときだけ、候補の `<Title>_automaster.wav` を `<Title>.wav` にコピーします。

## 数値の意味を伝えて、気になる所を聞く

実行した後、AIは `MASTER-REPORT.md` の数値を表にし、各行に意味を1行ずつ添えて見せます。例えばTrue Peakには「0に近いと再生機器で音が割れる」と書きます。最後に、聴いてみてこもる・低音が重いなど気になる所があれば教えてほしい、と1行添えます。聴くかどうかは利用者が決め、感想があれば、AIがそれを次のような調整に置き換えて作り直します。

| 感想 | 試すこと |
|---|---|
| こもる・暗い | `--profile dark` |
| 高音がきつい・明るすぎる | `--profile bright` |
| 低音が主役の曲（808・サブベース） | `--profile sub-driven` |
| 特定の帯域だけ | `--low` `--scoop` `--presence` `--shelf7k` `--harsh` `--air` でdBを上書き |

DAWなど別の方法でマスタリングした場合は、曲フォルダに `<Title>.wav` として置けば、`./next.sh` が目標の数値に収まっているかを確かめます。

## matcheringは任意で、同梱しない

お手本の曲に音色を全帯域で寄せたいときは、`--engine matchering --ref <参考曲.wav>` でmatcheringを使えます。matcheringは、参考曲に音色と音量を寄せるオープンソースのライブラリです。ライセンスがGPL-3.0のため公開版には同梱しておらず、使う方が自分で `pip install matchering` します。

`--ref` だけを渡すとエラーで止まるのは、うっかり別の曲に寄せないようにするためです。RESONALは最初matcheringの方式でしたが、手作業のマスターとブラインドで聴き比べたとき、僕は手作業のほうを選びました。参考曲の低音がその曲より薄く、自動のほうは低音が痩せていたためです。そこで僕が「手でやっているのは毎回ほぼ同じなので、テンプレート化したい」と伝え、AIが固定のイコライザの方式に作り替えました。もう一度聴き比べたときは、僕は自動のほうを選びました。

## 音源の長さは編集しない

マスタリングでは、音源の長さを変えません。器楽のイントロやアウトロ、最後の余韻も切りません。生成のときに「イントロ無し」と指示していても、出てきた音源の長さを正とします。長さが気に入らなければ、切るのではなく生成し直します。

## 後工程で、MVの音がマスターと同じか確かめる

マスタリングが終わったかどうかは、`./next.sh` が `<Title>.wav` をffmpegで実測して判定します。`MASTER-REPORT.md` があるだけでは通らず、実測が目標に収まっている必要があります。

MVの工程でも、書き出した本編の音とマスターを比べています。

```js:engine/steps.js
      const a = c.loudness(main); const m = c.loudness(c.file(`${c.title}.wav`));
      if (!a || !m || Math.abs(a.lufs - m.lufs) > 1) {
        return ai(`本編の音（${a && a.lufs} LUFS）がマスター（${m && m.lufs} LUFS）と違う`, `マスター確定後に作り直す: ${make}`);
      }
```

本編のIntegratedがマスターと1 LUFSを超えて違うと、マスタリング前の音源で書き出した疑いがあるとして、作り直しを指示します。ファイル名ではなく実測で比べているのは、名前が同じでも中身が違うことがあるためです。

## まとめ

マスタリングでは、セットアップで選んだ `streaming`（-14 LUFS / -1.0 dBTP）か `loud`（-9.5 LUFS / -1.5 dBTP）を目標に、`auto_master.py` を1回実行します。二重マスターを防いだうえで48kHz / 24bitにし、固定のイコライザで音色を整え、4倍で掛けるリミッタと実測を繰り返して数値に着地させます。判定がPASSのときだけ `<Title>.wav` に昇格し、気になる所があれば感想をプロファイルの調整に置き換えて作り直します。
