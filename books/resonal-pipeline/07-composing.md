---
title: "作曲 — Suno で2テイク作り、1つ選ぶ"
---

この章では、Suno で曲を作り、音源とカバー画像をそろえるまでを説明します。作曲は、僕が判断する3か所のうちの2つ目です。

## 流れ

作曲は次の順で進めます。

1. AI が Suno に渡す4つのテキストを書き、検査を通す
2. Suno で1回だけ生成し、できた2テイクの URL を Slack に送る
3. 僕が2テイクを聴いて、採用するほうの URL を返す（気に入らなければ作り直しを頼む）
4. AI が採用テイクの wav を取得する
5. AI がカバー画像を作る
6. MATERIAL 検査を通し、マスタリング（第8章）に進む

Suno は、歌詞とスタイルの説明文を入力すると、歌入りの曲を作ってくれる AI の作曲サービスです。1回の生成で、同じ入力から2つのテイク（別バージョン）ができます。

## Suno に渡す4つのテキスト

Suno とカバー画像の生成に使う文章は、曲フォルダに4つのテキストファイルとして書き出します。

| ファイル | 中身 |
|---|---|
| `suno_lyrics.txt` | 歌詞のかな版（第5章）。先頭に `[Intro]` を置かず、末尾を `[End]` にする |
| `suno_style.txt` | ジャンル・BPM・声・構成などを英語で書いたスタイルの説明（1000字以内） |
| `suno_exclude.txt` | 避けたい要素をカンマ区切りで並べたもの |
| `cover_prompt.txt` | カバー画像を生成するためのプロンプト |

例えば Stutter Step の `suno_exclude.txt` は次のとおりです。

```text:260905_Stutter Step/suno_exclude.txt
intro, outro, instrumental outro, long instrumental tail, fade out, shouting, screaming, raspy belting, gang chants, mature adult woman voice, sultry breathy alto, Western pop diva, cold deadpan vocal timbre, saccharine baby voice, breakbeat, amen break, sad, ballad, acoustic, rock guitar
```

4つのテキストは、Slack の曲ごとのスレッドにも1つずつ送ります。僕がスマホから中身を確認でき、必要ならそのまま Suno に貼り付けられるようにするためです。

## 4つのテキストの検査（SUNO-TXT）

4つのテキストは、`next.sh` の SUNO-TXT 検査を通してから使います。この検査は、これまでに Suno で実際に困ったことを、1つずつ検査に変えたものです。

| 検査 | 理由 |
|---|---|
| 歌詞の先頭に `[Intro]` が無い | Suno が楽器だけのイントロを付けるため |
| 歌詞の末尾が `[End]` | 楽器だけのアウトロで曲が引き伸ばされるのを防ぐため |
| 歌詞の漢字率が5%以下 | 漢字は読み間違いの原因になるため |
| ドロップ・ブレイクダウンの指示に `instrumental, no lyrics` がある | 指示の直後に歌詞行があると、Suno がそれを読み上げるため |
| スタイルに曲の長さを書かない | 長さを書くと、Suno がその長さまで楽器だけで埋めるため |
| スタイルが1000字以内 | Suno のスタイル欄の上限で、超えると貼れないため |
| スタイルで指定した語を、除外にも書いていない | 除外は語単位で働くので、狙った声質を自分で打ち消してしまうため |
| スタイルに `Japanese female vocal` がある | 書かないと、欧米の大人の女性の声になるため |
| カバーのプロンプトに `no text` などがある | 文字が入った画像は使えないため |

検査の一部は次のようなコードです。コメントにあるとおり、注意書きとして Skill に書くだけでは読み飛ばせるので、検査にしています。

```js:release/checklist.js
      const ly = get('suno_lyrics.txt');
      // ★踏んだ罠を検査に変換する（handoff-suno.md の注意書きは読み飛ばせるが、これは飛ばせない）
      if (/^\s*\[Intro\]/m.test(ly)) return 'suno_lyrics に [Intro] がある（Suno が器楽イントロを付ける）';
      if (!/\[End\]\s*$/.test(ly.trim())) return 'suno_lyrics の末尾が [End] でない（アウトロ水増しの防止）';
      if (kanjiRatio(ly) > 0.05) return `suno_lyrics に漢字が残っている（漢字率 ${(kanjiRatio(ly) * 100).toFixed(1)}%＝読み間違いの原因）`;
```

## 生成は1回、2テイクから選ぶ

検査を通ったら、Suno で曲を1回だけ生成します。

生成は自動でやり直しません。`CLAUDE.md` に、外部サービスへの試行は失敗そのものが相手側に積み重なる（利用回数の上限やアカウントの評価など）ので、試す前に立ち止まる、というルールを書いているためです。作り直すときも、僕の指示を4つのテキストに反映してから、1つの指示につき1回だけ生成します。

また、Suno の入力フォームは、前の曲で入力した値が残ります。実際に、ある曲の2テイクが前の曲の名前で保存されたことがありました。そのため、毎回どの欄も入れ直すようにしています。

## 僕がやるのは、聴いて URL を返すこと

2テイクの URL は、Slack の曲のスレッドに届きます。僕はスマホで2テイクを聴き、採用するほうの URL を返します。どちらも気に入らなければ、直してほしい点を伝えて作り直してもらいます。

URL を受け取ったら、AI がスクリプトで採用テイクの wav を取得し、曲フォルダに `audio.wav` として保存します。そのあとは僕の返事を待たずに、マスタリングと MV の制作に進みます。

## 生成された音源の長さは編集しない

RESONAL では、Suno が生成した音源の長さを編集しないことにしています。楽器だけのイントロやアウトロが長くても切りませんし、最後の余韻も削りません。スタイルで「イントロなし」「最後の歌詞でぴたっと止める」と発注していても、出てきた音源の長さのほうを正とします。

これは、僕が「イントロ・アウトロがあるから切る、という考え方はやめてください」と伝えて決めたルールです。`MASTERING.md` には、その理由として「RESONAL は生成された音楽そのものを作品として扱う」と書いています。長さが気に入らなければ、切るのではなく作り直します。長くなりすぎないようにしたい場合は、作詞や構成の段階で歌の部分を増やします。

Stutter Step では、採用したテイクの歌が2分15秒で終わり、そのあとに楽器だけのアウトロが約42秒続きました。僕は「アウトロが長すぎる」と伝えましたが、切ることはせず、作り直すことにしました。ただ、丸ごと作り直してもアウトロは消えませんでした。そこで僕は、Suno は3分以上にしたがっていて、歌詞が BPM や発話量に対して少ないのだと考え、サビの回数はそのままでラップのパートとアウトロ用の歌詞を足してもらいました。あわせて、`release.json` に目標の長さ（`"suno_length_target": "3:00"`）を書いたうえで、スタイルに長さを明示しています。最終的な音源の長さは180.44秒で、目標の3分に収まりました。

MATERIAL 検査で音源が135秒（2分15秒）より短いものを弾いているのも、同じ考え方です。歌の部分が短いと、Suno が楽器だけのアウトロで長さを埋めるので、歌詞の側で長さを確保するようにしています。

## BPM は発注値ではなく実測値を使う

スタイルに BPM を書いても、その BPM の曲が出てくるとは限りません。ある曲では、企画書に BPM 122 と書いて発注しましたが、できた音源を測ると 126.05 でした。発注値のまま MV でキャラクターが跳ねるリズムを組んだため、僕が見たときに「上下に跳ねるリズムが若干ずれている」状態になっていました。

そこで、BPM と拍の位置は、できた音源から測った値を使うようにしています。測るのは `tools/estimate_tempo_sections.py` です。

```bash
python3 tools/estimate_tempo_sections.py <audio.wav>
```

このスクリプトは、低音域の音の立ち上がり（キック）の強さから、BPM と拍の位置の組み合わせを総当たりで探します。さらに、高音域（ハイハットなど）でも別に同じ推定をして、2つの結果が一致するかを確かめます。最初に使っていた別のスクリプトは、先ほどの曲で 123.0 を返して外れていたので、ツールの出力も1つだけでは信じないようにしています。Bubble Trouble のように、曲の途中でテンポが 136.2 から 138.4 へ少しずつ上がる曲もあるため、区間ごとにテンポを測れるようにしています。

## カバー画像

音源と並行して、AI がカバー画像を2枚作ります。

| ファイル | 比率 | 用途 |
|---|---|---|
| `cover.png` | 16:9 | MV の背景、サムネイルの素材 |
| `cover_square.png` | 1:1 | SoundCloud や配信サービスのジャケット |

生成には ChatGPT の画像生成を使っています。`cover_prompt.txt` を入力にして、スクリプトから Codex CLI 経由で呼び出しています。

プロンプトでは、キャラクターの表情を細かく指定します。以前、生成した画像を見た僕が「この表情、ChatGPTって感じというかAIっぽい。もっと表情を作った方がAIぽさがなくなりそう」と伝えたことがあったためです。「笑顔」とだけ書くと無難な平均的な顔になりやすいので、表情のブロックをプロンプトの先頭近くに置き、`Absolutely NOT a neutral polite smile.` のように平均的な顔を否定形で禁じています。

また、画像には文字を入れません。曲名はサムネイルを作るときに後から乗せます。

## 素材がそろったかを検査する（MATERIAL）

音源とカバー画像がそろったら、MATERIAL 検査を通します。ファイルがあるだけでは通さず、0バイトや壊れたファイルを弾くために、中身を実際に読んで確かめています。

```js:release/checklist.js
      const a = ctx.loudness(path.join(ctx.dir, 'audio.wav'));
      if (!a) return 'audio.wav が読めない（0バイト/壊れている）';
      const dur = ctx.duration(path.join(ctx.dir, 'audio.wav'));
      if (dur !== null && dur < 135) return `尺が ${dur.toFixed(0)}秒（2:15未満＝器楽アウトロで水増しされた疑い。歌詞側で尺を担保する）`;
      const c16 = ctx.imageSize(path.join(ctx.dir, 'cover.png'));
      if (!c16) return 'cover.png が画像として読めない';
      if (Math.abs(c16.w / c16.h - 16 / 9) > 0.18) return `cover.png が 16:9 でない（${c16.w}x${c16.h}）`;
      const c1 = ctx.imageSize(path.join(ctx.dir, 'cover_square.png'));
      if (!c1) return 'cover_square.png が画像として読めない';
      if (Math.abs(c1.w / c1.h - 1) > 0.02) return `cover_square.png が 1:1 でない（${c1.w}x${c1.h}）`;
```

音源は ffmpeg で音量を測れるか（デコードできるか）と長さを、カバー画像は縦横の比率を確かめています。この項目は、僕が URL を返すのを待つ場所でもあるので、`next.sh` はここで「人の作業待ち」として止まります。

## まとめ

作曲では、AI が4つのテキストを書いて検査を通し、Suno で1回だけ生成して、僕が2テイクから1つを選びます。生成された音源の長さは編集せず、BPM は発注値ではなく実測値を使います。音源とカバー画像は、中身を読んで確かめてから次の工程に進みます。
