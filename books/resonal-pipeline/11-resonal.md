この章では、公開版のワークフローにはなく、RESONAL の実際の環境で足している仕組みを紹介します。

RESONAL の環境には、曲を作りながら継ぎ足してきた仕組みが多くあります。公開版では、これらを外して単純にしました。ここでは、そのうち4つを短く紹介します。

## MV の見せ方を、13のスタイルと18の軸で選ぶ

RESONAL では、MV の見せ方を「スタイル」と「軸」の2段階で決めています。

- **スタイル**：見せ方の型です。「白い図形と極太ゴシックの白黒反転」「黒と赤のゴシック」のように、書体・配色・動きの組み合わせに名前を付けたもので、2026年10月時点で13あります
- **軸**：MV を作るときに決める項目を、1つずつに分けたものです。歌詞の出し方（6）、キャラクターの動かし方（6）、背景（4）、打点（音の強い瞬間に入れる演出・2）の4分類で、合計18あります

スタイルは、18の軸の値をまとめて決めたプリセットという位置づけです。スタイルを採用しても、軸は1つずつ選び直してよいことにしています。

### 選定表と軸表を書いてから決める

新曲の MV に入るときは、頭に浮かんだ1つで進めず、13のスタイルを1行ずつ評価した選定表を書いてから、採用1つと対抗1つに絞ります。直近3曲で使ったスタイルを選ぶときは、理由を書きます。惰性で同じスタイルに戻ることがよく起きるためです。

次に、18の軸を1つずつ埋めて `STYLE-SELECTION.md` に書きます。このとき、既定のままにする軸も省略せず、「既定」と理由を書きます。省略を許していた頃、打点の演出を曲の最初から最後まで入れていた曲がありましたが、それは選んだ結果ではなく初期値のままだったことが後で分かったためです。

18の軸は、その曲で最も多く使う値です。シーンごとに変える軸は、MV の演出設計書 `DIRECTION.md` に、変える軸だけを書いて上書きします。

### Dive Reflex の例

Dive Reflex は、うるさい地上から息ひとつで潜り、音のない底を見て、何事もなかった顔で浮かんでくる曲です。この曲では、企画の前に僕から「three.js や Blender MCP でリアルな水辺を構築し、そこで彩瀬の2D素材を配置したり動かしたりする MV にしたい」と伝えていました。

![Dive Reflex（gothic3d）。夕方の桟橋から潜り、底に仰向けになって、夜の水面に浮かんでくる](/images/resonal-pipeline/style-dive-reflex.jpg)
*Dive Reflex（gothic3d）。夕方の桟橋から潜り、底に仰向けになって、夜の水面に浮かんでくる*

選定表では、3D空間をカメラで動かし、キャラクターを平面で置く型が既に実装されている gothic3d を採用しました。ただし、持ってきたのは3D空間・カメラ・キャラクターの平面といった骨組みだけで、血赤の配色や部品は持ってこず、世界はリアルな入り江に差し替えています。

軸表からいくつか抜粋すると、次のようになります。

| 軸 | 値 | 理由（要約） |
|---|---|---|
| 歌詞の配置 | 下帯・左下 | 画面の中央は水面の境界とキャラクターの居場所なので、歌詞は字幕の位置に退ける |
| 歌詞の書体 | 明朝 | 極太ゴシックはリアルな風景の上で浮くため、細い明朝の白にする |
| 打点の抜き方 | 光ワイプ | 暗転は溺れる方向に読まれるため、水面の膜が画面を横切る光にする |

選定表と軸表は、次の節のチェックで機械が検査しています。カタログの全スタイル名が選定表に出てくるか、18の軸コードが1つも欠けずに書かれているかを確かめ、書かれていなければ次の工程に進めません。

## 31項目のチェックと、毎晩20時の監査

公開版の `next.sh` は、6つの工程それぞれで成果物を軽く検査し、次にやることを1件だけ返します。RESONAL の環境では、同じ役割の検査項目を `checklist.js` という1つのファイルに定義していて、2026年10月時点で31項目あります。企画から、歌詞・スタイル選定・マスタリング・MV・リリース・引き継ぎメモまでを含みます。

1曲を終えるときは、`finalize.sh` というスクリプトを使います。機械で埋められる項目を埋めてからもう一度検査し、残った項目を「何をすればよいか」付きで列挙して、exit code 1 で止まります。exit code は、プログラムが終わるときに返す数値で、0 が成功、それ以外が失敗を表します。AI には exit code 0 が返るまで繰り返すよう指示していて、0 を見ないまま「完了しました」と報告することは禁止しています。

![ある曲のリリース工程を閉じたときの Claude Code の画面（当時は26項目）](/images/resonal-pipeline/finalize-exit0.jpg)
*ある曲のリリース工程を閉じたときの Claude Code の画面（当時は26項目）*

MV のレンダー後のセルフ検品も、この項目の1つです。スクリプトが決まった点のフレームを取り出してコンタクトシートを作り、黒い区間や音量を測ります。それを観て OK か NG かを判定するのは AI で、判定と NG への対応を書いたファイルがないと次に進めません。フレームを取り出す点を固定しているのは、AI が勘で選んだ点だけを見て、2回見誤ったためです。

### 毎晩20時に、実際の状態と照らし合わせる

リリース後は、mac mini で毎晩20:00に監査のスクリプトを動かしています。本編の公開が19:00、ショートの公開が19:10なので、その直後に結果を確かめる時刻にしています。

監査では、`release.json`（曲ごとのリリースの記録）と、YouTube の API などから取った実際の状態を照らし合わせます。例えば、公開時刻を過ぎた本編が公開されているか、YouTube に上がっている動画のバイト数が手元の納品ファイルと同じか、公開済みのショートに本編へのリンクが付いているか、といった項目です。

バイト数の照合は、おかわりアポカリプスで、マスタリング前の動画が本編として公開されていたことから足しました。アップロードのスクリプトが「曲フォルダの中で最もサイズが大きい動画」を本編として選ぶ作りになっていて、残っていたマスタリング前の動画のほうが大きかったためです。長さはどちらも同じ186秒だったので、僕が指摘するまで機械では検知できていませんでした。

違反が1件もなければ、Slack には何も送りません。違反があったときだけ、件数と内容、直すためのコマンドを送ります。また、YouTube のトークンが失効したときなど、監査そのものが失敗したときも Slack に送ります。何も届かないときに、「違反がない」のか「監査が動いていない」のかを区別するためです。

## 「動いた」と「意図どおりになった」は別物

長い自動処理を任せる中で、処理は最後まで動いてエラーも出ていないのに、成果物が意図どおりになっていなかった事故が何度かありました。そのうち2つを紹介します。

1つ目は、2026年9月に公開済みの Killframe のショートで起きました。ショートに本編へのリンクを付けるスクリプトが、保存したあとの状態を読み取れなかったときでも、exit code 0 を返していました。呼び出し側はそれを見て「✅ 関連動画リンク」と記録していましたが、実際にはリンクが付いていませんでした。

2つ目は、2026年9月8日から11日にかけて2回起きました。長い処理の出力を短くするために、`./tools/run_mv.sh ... | tail -5` のようにパイプで繋いで実行していました。パイプで繋ぐと、全体の exit code は最後のコマンド（`tail`）のものになります。そのため、MV のレンダーが途中で失敗していても、AI は exit code 0 を見て、最後まで終わったと判断していました。

この2つから、次の原則を決めました。

| 原則 | きっかけ |
|---|---|
| 確認できたものだけを成功とし、確認できなかったものは失敗として返す | 1つ目 |
| 失敗は握りつぶさずに Slack へ通知し、毎晩の監査で数える | 1つ目 |
| 結果を確かめたい処理はパイプで繋がない。繋ぐなら `set -o pipefail` を付ける | 2つ目 |
| exit code 0 の前に、成果物そのものを `ls` や `ffprobe` で確かめる | 2つ目 |

レンダーのスクリプトでは、動画を書き出すたびに `ffprobe` で長さを測り、決めた秒数より短ければ止めています。レンダーに使っている Remotion は、素材が見つからないなどの理由で失敗しても exit code 0 を返すことがあるためです。

これらの原則のうち、AI の作業ルールとして書けるものは、公開版の `CLAUDE.md` にも入れています（「exit 0 を信じず、成果物を見る」の節）。

## まだうまくいっていないこと

最後に、RESONAL の環境で、まだうまくいっていないことを書きます。

- **MV は一発では仕上がらない**：AI が最初に出してくる動画は、そのまま公開できる品質にはまだ届かないことが多いです。レビューの往復は、少ない曲で5回、多い曲では20回ほどになります
- **番号付きスクリプトに世代の差がある**：MV のスクリプトは、新しいプロジェクトを作るたびにテンプレートからコピーしています。そのため、テンプレートを改善しても、古いプロジェクトには反映されません
- **「パイプで繋がない」は、ルールに留まっている**：AI がスクリプトを呼び出すときのパイプの扱いは、`CLAUDE.md` に書いた運用ルールで、機械では防げていません
- **ドキュメントが実装に追いつかない**：この本を書くために実装を読み直したところ、`CLAUDE.md` には「22項目」と書いてあったのに、当時の `checklist.js` の項目は28あるなど、食い違いがいくつかありました

## まとめ

RESONAL の環境では、公開版に加えて、13のスタイルと18の軸で MV の見せ方を選ぶ仕組み、31項目のチェックと毎晩の監査を使っています。また、「動いた」と「意図どおりになった」を分けて確かめるようにしていますが、MV の往復の回数や、ルールに留まっている原則など、まだうまくいっていないこともあります。
