この章では、公開版のワークフローにはなく、RESONALの実際の環境で足している仕組みを紹介します。

RESONALの環境には、曲を作りながら継ぎ足してきた仕組みが多くあります。公開版の既定の流れでは、これらを外して単純にしました。ここでは、そのうち4つを短く紹介します。

## MVの軸の選び方を、さらに厳しくしている

18の軸と演出の辞書から選ぶ作り方は、「MV」の章で紹介したとおりです。RESONALでは、これを次のように厳しくしています。

- 新曲のMVに入るときは、13のスタイルを1行ずつ評価した選定表を書いてから、採用1つと対抗1つに絞る
- 直近3曲で使ったスタイルを選ぶときは、理由を書く。惰性で同じスタイルに戻ることがよく起きるため
- 18の軸は、既定のままにする軸も省略せずに書く。省略を許していた頃、打点の演出を全編に入れていた曲があり、選んだ結果ではなく初期値のままだったことが後で分かったため
- シーンごとに変える軸は、演出設計書 `DIRECTION.md` に上書きとして書く

選定表と軸表は、次の節のチェックで機械が検査しています。全スタイル名と18の軸コードが書かれていなければ、次の工程に進めません。

## 31項目のチェックと、毎晩20時の監査

公開版の `next.sh` は、6つの工程それぞれで成果物を軽く検査し、次にやることを1件だけ返します。RESONALの環境では、同じ役割の検査項目を `checklist.js` という1つのファイルに定義していて、2026年10月時点で31項目あります。企画から、歌詞・スタイル選定・マスタリング・MV・リリース・引き継ぎメモまでを含みます。

1曲を終えるときは、`finalize.sh` というスクリプトを使います。機械で埋められる項目を埋めてからもう一度検査し、残った項目を「何をすればよいか」付きで列挙して、exit code 1で止まります。exit codeは、プログラムが終わるときに返す数値で、0が成功、それ以外が失敗を表します。僕はAIにexit code 0が返るまで繰り返すよう指示していて、0を見ないまま「完了しました」と報告することは禁止しています。

MVのレンダー後のセルフ検品も、この項目の1つです。スクリプトが決まった点のフレームを取り出してコンタクトシートを作り、黒い区間や音量を測ります。それを観てOKかNGかを判定するのはAIで、判定とNGへの対応を書いたファイルがないと次に進めません。フレームを取り出す点を固定しているのは、AIが勘で選んだ点だけを見て、2回見誤ったためです。

### 毎晩20時に、実際の状態と照らし合わせる

リリース後は、mac miniで毎晩20:00に監査のスクリプトを動かしています。本編の公開が19:00、ショートの公開が19:10なので、その直後に結果を確かめる時刻にしています。

監査では、`release.json`（曲ごとのリリースの記録）と、YouTubeのAPIなどから取った実際の状態を照らし合わせます。例えば、公開時刻を過ぎた本編が公開されているか、YouTubeに上がっている動画のバイト数が手元の納品ファイルと同じか、公開済みのショートに本編へのリンクが付いているか、といった項目です。

バイト数の照合は、おかわりアポカリプスで、マスタリング前の動画が本編として公開されていたことから足しました。アップロードのスクリプトが「曲フォルダの中で最もサイズが大きい動画」を本編として選ぶ作りになっていて、残っていたマスタリング前の動画のほうが大きかったためです。長さはどちらも同じ186秒だったので、僕が指摘するまで機械では検知できていませんでした。

違反が1件もなければ、Slackには何も送りません。違反があったときだけ、件数と内容、直すためのコマンドを送ります。また、YouTubeのトークンが失効したときなど、監査そのものが失敗したときもSlackに送ります。何も届かないときに、「違反がない」のか「監査が動いていない」のかを区別するためです。

## 「動いた」と「意図どおりになった」は別物

長い自動処理を任せる中で、処理は最後まで動いてエラーも出ていないのに、成果物が意図どおりになっていなかった事故が何度かありました。そのうち2つを紹介します。

1つ目は、2026年9月に公開済みのKillframeのショートで起きました。ショートに本編へのリンクを付けるスクリプトが、保存したあとの状態を読み取れなかったときでも、exit code 0を返していました。呼び出し側はそれを見て「✅ 関連動画リンク」と記録していましたが、実際にはリンクが付いていませんでした。

2つ目は、2026年9月8日から11日にかけて2回起きました。長い処理の出力を短くするために、AIが `./tools/run_mv.sh ... | tail -5` のようにパイプで繋いで実行していました。パイプで繋ぐと、全体のexit codeは最後のコマンド（`tail`）のものになります。そのため、MVのレンダーが失敗していても、AIはexit code 0を見て、最後まで終わったと判断していました。

この2つから、次の原則を決めました。

| 原則 | きっかけ |
|---|---|
| 確認できたものだけを成功とし、確認できなかったものは失敗として返す | 1つ目 |
| 失敗は握りつぶさずにSlackへ通知し、毎晩の監査で数える | 1つ目 |
| 結果を確かめたい処理はパイプで繋がない。繋ぐなら `set -o pipefail` を付ける | 2つ目 |
| exit code 0の前に、成果物そのものを `ls` や `ffprobe` で確かめる | 2つ目 |

レンダーのスクリプトでは、動画を書き出すたびに `ffprobe` で長さを測り、決めた秒数より短ければ止めています。レンダーに使っているRemotionは、素材が見つからないなどの理由で失敗してもexit code 0を返すことがあるためです。

これらの原則のうち、AIの作業ルールとして書けるものは、公開版の `CLAUDE.md` にも入れています（「exit 0を信じず、成果物を見る」の節）。

## まだうまくいっていないこと

- MVは一発では仕上がらない：AIが最初に出してくる動画は、そのまま公開できる品質にはまだ届かないことが多いです。レビューの往復は、少ない曲で5回、多い曲では20回ほどになります
- 番号付きスクリプトに世代の差がある：MVのスクリプトは、新しいプロジェクトを作るたびにテンプレートからコピーしています。そのため、テンプレートを改善しても、古いプロジェクトには反映されません
- 「パイプで繋がない」は、ルールに留まっている：AIがスクリプトを呼び出すときのパイプの扱いは、`CLAUDE.md` に書いた運用ルールで、機械では防げていません
- ドキュメントが実装に追いつかない：この本を書くために実装を読み直したところ、`CLAUDE.md` には「22項目」と書いてあったのに、当時の `checklist.js` の項目は28あるなど、食い違いがいくつかありました

## まとめ

RESONALの環境では、公開版に加えて、MVの軸の選び方を厳しくする仕組み、31項目のチェックと毎晩の監査を使っています。また、「動いた」と「意図どおりになった」を分けて確かめるようにしていますが、MVの往復の回数や、ルールに留まっている原則など、まだうまくいっていないこともあります。
