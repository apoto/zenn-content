---
title: "「動いた」と「意図どおりになった」は別物"
---

この章では、長い自動処理を AI とスクリプトに任せる中で起きた事故のうち、同じ型の3つを紹介し、そこから決めた原則と、スクリプトでの守り方を説明します。

## 3つの事故に共通すること

RESONAL の `CLAUDE.md`（第3章）には、作業のルールとあわせて、そのルールを足すきっかけになった事故を記録しています。そのうち3つは、同じ型の事故でした。

どれも、処理は最後まで動いていて、エラーも出ていません。しかし、成果物は意図どおりになっていませんでした。つまり、「動いた」ことを確かめただけで、「意図どおりになった」ことは確かめていませんでした。

以下、3つを順に紹介します。

## 事故1：保存を確認できないのに、成功を返していた

2026年9月、公開済みの Killframe のショートで起きた事故です。

第14章で説明したとおり、ショートには本編へのリンクを付けています。このリンクを付けるスクリプトは、保存したあとの状態を読み取れなかったときでも、exit code 0（成功）を返していました。exit code は、プログラムが終わるときに返す数値で、0 が成功、それ以外が失敗を表します。

呼び出し側は、この exit code を見て「✅ 関連動画リンク」と記録していました。しかし実際には、ショートに本編へのリンクが付いていませんでした。そのため、記録の上では成功のままになっていました。

直したことは次の3つです。

- リンクが付いたことを確認できなかったら、失敗として exit code 0 以外を返す
- 失敗したら、握りつぶさずに Slack へ通知する
- 毎晩の監査で、リンクが付いていないショートを数える（第14章）

1つ目だけでは足りない理由は、失敗を返すようにしても、その日の再試行が続けて失敗すると、そのまま放置されるためです。そこで、失敗を通知し、残っているものを毎晩数える仕組みもあわせて入れました。

## 事故2：パイプで終了コードが消えた

2026年9月8日から11日にかけて、2回起きた事故です。

長い処理の出力を短くするために、次のようにパイプで `tail` に繋いで実行していました。

```bash
./tools/run_mv.sh "<曲フォルダ>" "<本文>" | tail -5
echo $?
```

パイプで繋ぐと、全体の exit code はパイプの最後のコマンド（ここでは `tail`）のものになります。`tail` は出力を表示できれば 0 を返すので、`run_mv.sh` が失敗していても、全体としては 0 になります。

`run_mv.sh` は、ミュージックビデオのレンダー・検査・Slack への配信を順に行うスクリプトです（第12章）。このとき `run_mv.sh` は途中で失敗して止まっていましたが、AI は exit code 0 を見て、レンダーが最後まで終わったと判断していました。

2回目は、複数のコマンドを `;` で繋いだ行の最後に `| tail` を付けていたために、本体の出力まで捨てていました。このときは、3×3 のグリッドの生成で成果物が出来ていないのに exit code 0 になっていました。

ここから決めたのは、次のことです。

- 結果を確かめたい処理は、単独で実行し、パイプで繋がない
- 繋ぐ場合は `set -o pipefail` を付ける（パイプの途中で失敗したら、全体を失敗にするシェルの設定）
- exit code 0 を成功の根拠にする前に、成果物そのものを `ls` や `ffprobe` で確かめる

```bash
set -o pipefail
./tools/run_mv.sh "<曲フォルダ>" "<本文>" | tail -5
echo $?   # run_mv.sh が失敗していれば 0 以外になる
```

## 事故3：数えずに申告した

最後は、AI の報告で起きた事故です。ある語が何回出てくるかを、実際に数えずに文章に書いていました。あとで数えると実際の回数とズレていて、2件を修正しました。【要確認: 何の語を、どの文書で数えた件か】

これはスクリプトではなく、AI の報告の話です。しかし、「0件です」「問題ありません」と確かめずに書く、という点で、事故1〜3と同じ型だと考えています。そこで `CLAUDE.md` には、「0件」「問題なし」と書く前に、数えるか、検査を通すことをルールとして書いています。

## 決めた原則

3つの事故から、次の原則を決めました。

| 原則 | きっかけ |
|---|---|
| 確認できたものだけを成功とし、確認できなかったものは失敗として返す | 事故1 |
| 失敗は握りつぶさずに Slack へ通知し、毎晩の監査で数える | 事故1 |
| 結果を確かめたい処理はパイプで繋がない。繋ぐなら `pipefail` を付ける | 事故2 |
| exit code 0 の前に、成果物そのものを `ls` や `ffprobe` で確かめる | 事故2 |
| 「0件」「問題なし」と書く前に、数えるか、検査を通す | 事故3 |

## スクリプトでの守り方

ここからは、これらの原則をスクリプトでどう守っているかを説明します。

### レンダーのあとに、動画の中身を確かめる

ミュージックビデオのレンダーには Remotion を使っています。Remotion は、素材のファイルが見つからないなどの理由で失敗しても、exit code 0 を返すことがあります。そのため、`set -e`（コマンドが失敗したらスクリプトを止めるシェルの設定）だけでは止まりません。

そこで、レンダーのスクリプトでは、動画を書き出すたびに、出来た動画を確かめています。

```zsh:projects/mv-template/tools/04_render.sh
need() {
  local f="$1" min="$2"
  [ -s "$f" ] || { echo "[NG] 出来ていない: $f" >&2; exit 4; }
  local d; d="$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$f" 2>/dev/null || echo 0)"
  awk -v d="$d" -v m="$min" 'BEGIN{ if (d+0 < m+0) exit 1 }' \
    || { echo "[NG] 尺が短すぎる: $f (${d}s < ${min}s)＝レンダーが途中で落ちている" >&2; exit 4; }
}
echo "=== ShortVideo ==="; npx remotion render ShortVideo "$SONG/${TITLE} (Short).mp4" --log=error
need "$SONG/${TITLE} (Short).mp4" 10
echo "=== LyricVideo ==="; npx remotion render LyricVideo "$SONG/${TITLE}.mp4" --log=error
need "$SONG/${TITLE}.mp4" 60
```

`need()` は、ファイルが空でないかを確かめたあと、`ffprobe` で動画の長さを測り、決めた秒数より短ければ exit code 4 で止まります。ショートは10秒、本編は60秒を下限にしています。Remotion の exit code ではなく、出来た動画の中身で成功を判断しています。

### 文字起こしのあとに、結果のファイルを確かめる

歌詞のタイミングを取るための文字起こしには Whisper を使っています。Whisper も、モデルのダウンロードに失敗したときなどに、exit code 0 を返すことがあります。そこで、文字起こしのスクリプトでも、結果のファイルが出来ているかを確かめています。

```zsh:projects/mv-template/tools/01_transcribe.sh
ffmpeg -y -i "$AUDIO" -ar 16000 -ac 1 "$OUT/audio_16k.wav" -loglevel error
echo "[whisper] transcribing (medium, language=$LANG_CODE)…"
whisper "$OUT/audio_16k.wav" --language "$LANG_CODE" --model medium --word_timestamps True \
  --output_format json --output_dir "$OUT" --fp16 False
# ★成果物を検査してから成功を名乗る（whisper はモデルDLに失敗しても 0 を返すことがある）
[ -s "$OUT/audio_16k.json" ] || { echo "[NG] $OUT/audio_16k.json が出来ていない（whisper が落ちた）" >&2; exit 4; }
```

### 検査に落ちたら、次へ進まない

事故3に出てきた `run_mv.sh` は、レンダー（`04_render.sh`）、検査（`07_verify.sh`）、Slack への配信（`05_deliver_slack.sh`）を順に呼ぶだけのスクリプトです。`set -eu` を付けているので、途中のスクリプトが exit code 0 以外を返したら、そこで止まります。検査に落ちた動画が Slack に配信されることはありません。

また、第15章の `checklist.js` でも、ミュージックビデオの項目で動画がデコードできるかを確かめています。レンダーの途中でディスクの空きが足りなくなると、Remotion は何も言わずに壊れた動画を書き出すことがあるためです。

### pipefail はスクリプトに入っていない

正直に書くと、パイプの原則はスクリプトにはほとんど入っていません。

ミュージックビデオの番号付きのシェルスクリプト（`01`〜`07` など）は、`set -eu` だけで、`pipefail` は付けていません。リポジトリ全体でも、`pipefail` を付けているシェルスクリプトは、第2章の `next.sh`、クレジット表記を検査する `check-mv-credits.sh` など5本です。

番号付きスクリプトの中にも、パイプはあります。例えば検査の `07_verify.sh` は、動画をデコードしたときの ffmpeg のエラー出力をパイプで `wc -l` に渡し、その行数が0かどうかで判定しています。この箇所は、ffmpeg の exit code ではなく出力の中身で判定しているので、`pipefail` がなくても判定できます。ただ、番号付きスクリプトの中のパイプが、どれもこの考え方で書かれているかは、まだ点検できていません。

また、事故2はスクリプトの中ではなく、AI がスクリプトを呼び出すときにパイプで繋いだことで起きました。この部分は `CLAUDE.md` の運用ルールとして書いているだけで、機械では防げていません。

## まとめ

3つの事故は、どれも処理が最後まで動き、エラーも出ていないのに、成果物が意図どおりになっていなかったものです。そこから、確認できたものだけを成功とする、パイプで exit code を消さない、exit code 0 の前に成果物を確かめる、という原則を決めました。レンダーや文字起こしのスクリプトでは、道具の exit code ではなく、出来たファイルの中身で成功を判断しています。一方で、AI がコマンドを呼び出すときのパイプの扱いは、まだ運用ルールに留まっています。
