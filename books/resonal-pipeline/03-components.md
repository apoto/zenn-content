この章では、RESONAL の制作を動かしている仕組みを、4つの層に分けて説明します。

## 4つの層

RESONAL の制作は、次の4つの層で動いています。

| 層 | 役割 | 実体 |
|---|---|---|
| 振る舞いのルール | AI がどう振る舞うか | `CLAUDE.md` |
| 手順書 | 各工程のやり方 | Skill（`.claude/skills/`） |
| スクリプト | 決まった処理と検査 | シェル・Node.js・Python |
| 自動実行 | 時間になったら動く処理 | launchd |

【画像: 4層の構成図】

AI（Claude Code）は、`CLAUDE.md` のルールに従い、Skill の手順を読みながら、スクリプトを呼び出して作業します。人がいない時間の処理は、launchd が決まった時刻に実行します。

以下、層ごとに説明します。

## 振る舞いのルール：CLAUDE.md

リポジトリの直下に置いた `CLAUDE.md` には、2種類のことを書いています。

1つは **彩瀬??としての人格** です。一人称や口調、性格を定めていて、Claude Code はこのリポジトリで作業するとき、彩瀬??として僕と会話します。

もう1つは **作業のルール** です。例えば次のようなものがあります。

- ファイルを編集したら、すぐに commit と push をする（2台の Mac で同期するため）
- 動画や画像を作ったら、確認を待たずに Slack へ送る（僕がスマホで確認するため）
- 生成された音源の長さは編集しない
- 外部サービスを操作する前に、仕様とログイン状態を確認する

このルールの多くは、実際に起きた失敗から足したものです。どんな失敗から何を足したかは、第16章で紹介します。

## 手順書：Skill

Skill は、特定の作業の手順を書いた Markdown ファイルです。Claude Code は、依頼の内容に合った Skill を読み込んでから作業します。

RESONAL では、リポジトリの `.claude/skills/` に Skill を置いています。リポジトリに置くことで、2台の Mac のどちらで作業しても同じ Skill が使えます。

2026年9月時点で29本あり、分類すると次のようになります。

| 分類 | 主な Skill |
|---|---|
| 全体の進行 | `compose-song` |
| 企画・作詞 | `song-concept-jp`、`lyric-writing-jp`、`cyber-jpop-suno` |
| マスタリング | `mixmaster-resonal` |
| MVの見せ方の選定 | `mv-styles`、`mv-cut-editing`、`mv-reference-ingest` |
| MVのスタイル別の作り方 | `style-demonlord`、`style-snaptype`、`style-negaposi` など9本 |
| キャラクターの動かし方 | `puppet-rig`、`bounce-rig`、`kling-living-loop`、`kling-loop-render` |
| 3D の表現 | `render-3d-look`、`water-3d` |
| サムネイル | `thumbnail-maker` |
| 配信 | `distrokid-distribute`、`distrokid-ep-upload` |

Skill には、手順だけを書くようにしています。命令形の1行ルール、コマンド、ファイルのパス、数値です。「以前こういう失敗があった」という経緯は書きません。経緯は制作ログと git の履歴に残っているので、Skill に書くと同じことが2か所に残り、読むたびに本質が分かりにくくなるためです。

Skill を更新したら、`skill-lint.sh` という検査スクリプトを通します。経緯の書き込みが残っていないか、参照しているファイルのパスが実在するかを機械で確認しています。

## スクリプト：決まった処理と検査

AI に毎回考えさせる必要のない処理は、スクリプトにしています。大きく分けると次の3種類です。

- **進行の管理**：`next.sh`（次にやることを返す）、`finalize.sh`（残りの項目を埋めて完了を判定する）
- **制作の処理**：MV の番号付きスクリプト（`01`〜`07`）、マスタリングの `auto_master.py` など
- **外部への投稿**：YouTube へのアップロード、SNS の予約投稿、Slack への送信

スクリプトにする基準は「毎回同じ手順で、結果を機械で確かめられること」です。例えば動画のレンダーは、手順が決まっていて、壊れていないかを ffmpeg で確かめられます。一方で、歌詞を書くことや、MV の見せ方を選ぶことは、AI が Skill を読んで判断します。

## 自動実行：launchd

mac mini では、launchd（macOS の定時実行の仕組み）で次のような処理を動かしています。

| 処理 | タイミング | 内容 |
|---|---|---|
| SNS の予約投稿 | 30分ごと | 予約された投稿を、時刻になったら X と Threads に送る |
| ショート動画の自動公開 | 本編の公開10分後 | ショートの公開、本編とのリンク、コメント、X での告知 |
| リリースの監査 | 毎晩20時 | 全曲の記録と、YouTube などの実際の状態を照らし合わせる |
| プレイリストの同期 | 毎晩21時半 | 新曲を YouTube のプレイリストに追加する |

監査は、ズレが見つかったときだけ Slack に通知します。ズレが無ければ何も送りません。そのため、Slack に通知が来たときは、何か対応が必要な状態です。

## 2台の Mac の分担

2台の Mac は、ミュージックビデオが完成するところで担当を分けています。

- **MacBook**：企画からミュージックビデオの完成まで
- **mac mini**：リリース以降

分けている理由は、ショート動画の自動公開が、本編をアップロードしたパソコン上で実行されるためです。MacBook は常に起動しているわけではないので、公開日の朝に閉じていると、ショートが公開されません。そこで、リリースは常時起動している mac mini で行うことにしました。

この分担は、ルールとして書くだけでなく、スクリプトでも強制しています。リリースのコマンドを MacBook で実行すると、止まるようにしています。

```zsh:release/_terminal-guard.sh
if [ -z "${RESONAL_ALLOW_RELEASE_HERE:-}" ] && print -r -- "${HOST:-$(hostname)}" | grep -qi 'macbook'; then
  echo "[STOP] この端末は MacBook。リリース工程は mac mini で叩く。" >&2
  exit 9
fi
```

2台の間では、GitHub 経由でしかやり取りできません。そこで、片方の Mac で「もう一方でやってほしいこと」をファイル（`ops/inbox-macmini.md` など）に書いて push し、もう一方が作業を始めるときに読んで実行する、という運用にしています。

## まとめ

RESONAL の制作は、振る舞いのルール（CLAUDE.md）、手順書（Skill）、スクリプト、自動実行（launchd）の4層で動いています。判断が要る作業は AI が Skill を読んで行い、決まった処理と検査はスクリプトに任せています。次章からは、工程ごとに説明します。
