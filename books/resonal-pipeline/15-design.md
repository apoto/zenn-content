---
title: "進行を人が覚えない設計"
---

この章では、1曲の進行を僕も AI も覚えずに済むようにしている設計を説明します。第2章で紹介した `next.sh` と、第14章の `finalize.sh`・毎晩の監査が、どう同じ定義を共有しているかが中心です。

## 曲フォルダの中身から現在地を導く

RESONAL では、進行状況を記録するデータベースを持っていません。どの工程まで進んだかは、曲フォルダの中身と `release.json` から、その都度判定しています。

判定しているのは `next.js`（`next.sh` から呼ばれる本体）の次の関数です。

```js:release/next.js
function evaluate(ctx) {
  const rows = [];
  for (const ph of PHASES) {
    for (const it of items.filter((x) => x.phase === ph)) {
      let ap = true;
      try { ap = it.applies ? it.applies(ctx) : true; } catch { ap = true; }
      if (!ap) { rows.push({ it, state: 'skip' }); continue; }
      let r;
      try { r = it.check(ctx); } catch (e) { r = `check が例外: ${e.message}`; }
      rows.push({ it, state: r === true ? 'ok' : 'todo', reason: r === true ? null : r });
    }
  }
  return rows;
}
```

工程の順に項目を検査し、「この曲に当てはまらない（skip）」「済んでいる（ok）」「まだ（todo）」に分けます。`next.sh` は、このうち最初の todo を1件だけ表示します。

この形にしている理由は、第2章で説明したとおり、制作が数日から数週間に分かれるためです。進行状況を別の場所に記録すると、ファイルを直したのに記録を更新し忘れる、といったズレが起きます。曲フォルダの中身から毎回判定すれば、このズレは起きにくくなります。また、2台の Mac の間で同期するのも、曲フォルダ（git）だけで済みます。

`next.sh --list` を実行すると、制作中の曲ごとに現在地と残りの件数が表示されます。

## やることの定義は1つのファイルにまとめる

1曲でやることは、`release/checklist.js` という1つのファイルに定義しています。2026年9月27日時点で、9つのフェーズに28項目があります。

| フェーズ | 内容 | 項目数 |
|---|---|---|
| init | 曲フォルダと `release.json` の用意 | 1 |
| concept | 企画書、曲調台帳 | 2 |
| lyrics | 歌詞 | 1 |
| style | MV の見せ方の選定、Suno に渡す文章 | 2 |
| material | 音源とカバー画像 | 1 |
| master | マスタリング | 1 |
| mv | ミュージックビデオの演出・制作・検品・レビュー | 5 |
| release | 予告文、アップロード用の原稿、リリースの実行など | 12 |
| asset | 引き継ぎメモ、制作ログ、SoundCloud の準備 | 3 |

1つの項目は、次のような形で書いています。

| フィールド | 意味 |
|---|---|
| `id` / `label` | 項目の名前と、何をやるかの1行説明 |
| `phase` | どのフェーズに属するか |
| `who` | 誰がやるか（次の節で説明） |
| `applies` | この曲に当てはまるか |
| `check` | 済んでいれば `true`、まだなら理由の文字列を返す |
| `fix` | 機械で埋める処理（`who` が `auto` の項目だけ） |
| `instruct` | 何をどう書けばよいかの指示（AI や僕がやる項目） |

このファイルを、次の3つの道具が読んでいます。

| 道具 | 使い方 |
|---|---|
| `next.sh` | 最初の未了を1件だけ返す |
| `finalize.sh` | 機械で埋められる項目を埋め、残りを列挙する（第14章） |
| `release-audit.js` | 毎晩、`check` だけを使って未了を探す（第14章） |

項目を増やしたり直したりするときは、`checklist.js` だけを直します。すると、3つの道具の動きが同時に変わります。手順書や `CLAUDE.md` には項目の中身を書かず、「正本は `release/checklist.js`」とだけ書いています。同じことを2か所に書くと、片方だけ直して食い違うおそれがあるためです。

## 誰がやるかを3種類に分ける

各項目の `who` には、次の3種類のどれかを書きます。

| who | 意味 | 項目数 | 例 |
|---|---|---|---|
| `auto` | 機械が `fix` で埋める | 6 | ジャケット画像の生成、YouTube の予約、歌詞字幕の登録 |
| `claude` | AI が判断して書く | 20 | 企画書、歌詞、予告文、引き継ぎメモ |
| `human` | 僕の入力や確認が要る | 2 | 音源を選ぶ、ミュージックビデオのレビュー |

`next.sh` は、次の1件の `who` によって、終わり方を変えています。

| exit code | 意味 |
|---|---|
| 0 | 全工程が完了している |
| 1 | AI がやる項目がある（やったら、もう一度 `next.sh` を実行する） |
| 3 | 僕の番（AI は `next.sh` を繰り返さずに待つ） |

exit code は、プログラムが終わるときに返す数値です。AI はこの値を見て、作業を続けるか、僕を待つかを決めます。

第2章では、僕が判断するのは3か所と書きました。そのうち、曲を選ぶこととミュージックビデオのレビューの2つが `human` の項目です。残りの企画を選ぶ場面は、曲フォルダを作る前の `next.sh --new` で止まるようにしています（第4章）。

## 検査はファイルの有無ではなく中身で判定する

各項目の `check` は、できるだけファイルがあるかどうかではなく、中身を見て判定するようにしています。空のファイルを置いただけでは、先に進めないようにするためです。

例えば、音源とカバー画像の項目は次のように検査しています。

```js:release/checklist.js
    check: (ctx) => {
      const miss = ['audio.wav', 'cover.png', 'cover_square.png'].filter((f) => !ctx.exists(path.join(ctx.dir, f)));
      if (miss.length) return `apoto の手作業待ち: ${miss.join(', ')}`;
      // ★存在では通さない: 0バイト/壊れたファイルを「揃った」と誤認しない
      const a = ctx.loudness(path.join(ctx.dir, 'audio.wav'));
      if (!a) return 'audio.wav が読めない（0バイト/壊れている）';
      const dur = ctx.duration(path.join(ctx.dir, 'audio.wav'));
      if (dur !== null && dur < 135) return `尺が ${dur.toFixed(0)}秒（2:15未満＝器楽アウトロで水増しされた疑い。歌詞側で尺を担保する）`;
```

ファイルが揃っているかを見たあと、ffmpeg で音源の音量を実際に測れるか、長さが2分15秒以上あるかを確かめています。このあと、カバー画像の縦横比が16:9と1:1になっているかも確かめます。

ほかにも、次のような検査をしています。

- **マスタリング**：配信用の音源の音量とピークを ffmpeg で測り、基準値（第8章）の範囲に入っているか
- **ミュージックビデオ**：動画がデコードできるか、動画の音量と長さがマスタリング済みの音源と一致するか（一致しなければ、仮の音源でレンダーした疑いがある）
- **原稿**：予告文が X の文字数の上限に収まるか、SNS の文面で使わないと決めた語が入っていないか

ffmpeg で測る処理は時間がかかるので、ファイルの更新時刻とサイズをキーにして、測った結果を保存しています。ファイルが変わらなければ、2回目以降は保存した結果を使います。

一方で、中身まで見ていない項目もあります。ショート素材の設定ファイルや引き継ぎメモは、ファイルがあるかどうかだけを見ています。制作ログは、曲名が書かれているかだけを見ています。

## 新しいルールは、古い曲に当てない

`checklist.js` の項目は、運用しながら増えていきます。しかし、新しい項目をすでに作り終えた曲にまで当てると、過去の曲が「未了」として扱われます。その結果、監査が毎晩たくさんの違反を通知し、本当に対応が要る違反が埋もれてしまいます。

そこで、項目ごとに「いつ以降の曲に当てるか」を `release/policy.js` に書いています。基準の日付には2種類あります。

| 基準 | 意味 | 例 |
|---|---|---|
| 公開日 | YouTube の公開日。リリース済みの曲に遡らないために使う | 配信サービスへの入稿（2026-07-31 以降に公開する曲） |
| フォルダの日付 | 曲フォルダ名の先頭の日付（制作を始めた日）。公開日が決まっていない制作中の曲にも使える | MV の見せ方の18項目の選定（260904 以降に始めた曲） |

判定は次の関数で行っています。

```js:release/policy.js
function inPolicy(key, ctx) {
  if (ALL()) return true;
  const p = POLICIES[key];
  if (!p) throw new Error(`未知のポリシー: ${key}`);
  if (p.axis === 'folder') {
    const st = folderStamp(ctx.name);
    return st === null ? true : st >= p.from;      // 規約外の名前は対象に含める（見逃しより誤検知を選ぶ）
  }
  // publish 軸: 公開日が未定なら「これから公開する曲」なので対象
  return !ctx.releaseDate || ctx.releaseDate >= p.from;
}
```

フォルダ名が決まった形になっていない曲や、公開日が決まっていない曲は、対象に含めます。判定できないときは、見逃すより、余計に通知するほうを選んでいます。

過去の曲も含めて未了を洗い出したいときは、環境変数 `RESONAL_AUDIT_ALL=1` を付けて実行すると、全曲に当てて検査できます。

この日付を `policy.js` にまとめる前は、`checklist.js` と監査スクリプトにそれぞれ日付が書かれていました。しかも、公開日とフォルダの日付の2種類が混ざっていて、どの曲にどの項目が当てはまるのかが分かりにくくなっていました。

## 例外は宣言する

曲によっては、当てはまらない項目があります。例えば、配信サービスに出さない曲では、配信用のジャケット画像も入稿も要りません。

このような場合は、第13章で説明したとおり、`release.json` に `"dsp": "skip"` のような宣言を書きます。各項目の `applies` はこの宣言を見て、当てはまらない項目を skip にします。

```js:release/checklist.js
    applies: (ctx) => ctx.rj.dsp !== 'skip',
```

宣言には、ほかに次のようなものがあります。

- `"shorts": "skip"`：ショートを作らない
- `"shorts_farm": "skip"`：ショート素材を量産しない
- `"lyric_video": false`：歌詞を表示しないミュージックビデオなので、タイトルに `[Lyric Video]` を付けない
- `"captions": "skip"`：YouTube に歌詞字幕を付けない

宣言がなければ、項目は当てはまるものとして検査します。空欄のままにしておくと未了として扱われるので、「意図してやらない」と「忘れている」がファイルの上で区別できます。

## まとめ

進行状況はデータベースに持たず、曲フォルダの中身から毎回判定しています。やることの定義は `checklist.js` の1ファイルにまとめ、`next.sh`・`finalize.sh`・毎晩の監査の3つが同じ定義を読んでいます。検査はできるだけ中身を測って判定し、新しいルールは日付で区切って古い曲に当てないようにしています。当てはまらない項目は、`release.json` に宣言して外しています。
